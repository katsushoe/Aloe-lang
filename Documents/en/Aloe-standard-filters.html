Aloe Standard Library Specification (Filters)

Draft • English • Filters Library • version 40
This document is a separate “standard filters library specification” independent from the Aloe language specification.

0. Overview

This document defines a set of standard filters in Aloe, based on the concepts of pipe<T> and filter.

The core language specification defines syntax, the type system, and the pipe / filter constructs. This document is independent of that and describes the names, behavior, and types of the filters that are provided by default.

Implementations should aim to be “as faithful as possible” to the signatures and semantics defined here, but some behavior may depend on the implementation due to performance or platform differences.

NOTE: All code examples in this document are Aloe pseudo code and may be updated in the future as the language specification evolves.
Implementation status: This catalog remains a draft. The current compiler supports user-declared filters as source | filter(name) | destination; and the pipeline-only shorthand source |: name | destination;; documented parameterized standard filters use source |: name: "argument" | destination;. The standard tolower and toupper filters are implemented for pipe<string>, using culture-independent invariant case mapping. The ltrim, rtrim, and trim filters remove leading, trailing, or both-side Unicode whitespace, and lineSplit splits string chunks at LF boundaries while preserving partial lines across chunks. The camelcase, pascalcase, and snakecase filters split input into whitespace-separated words, normalize casing invariantly, and join words without separators or with underscores as appropriate. The startswith and contains filters pass matching strings using ordinal comparison; strstr passes only strings containing the argument and outputs the suffix beginning at its first occurrence. The join filter concatenates its input with the specified separator and emits one string, including an empty string for empty input. The quote_meta filter escapes regular-expression metacharacters for use in a literal pattern. The utf8 filter consumes all bytes, strictly decodes UTF-8 across chunk boundaries, and emits one string (empty input emits an empty string; invalid sequences raise a VM exception). The VM implements md4 as a full-stream byte filter that emits 16 digest bytes in order for legacy interoperability only, and implements sha1 and sha256 as full-stream byte filters that emit 20 and 32 digest bytes in order, respectively; MD4 and SHA-1 are not suitable for security-sensitive use. The VM also supports pipe<byte> and implements bin2hex, which consumes the byte stream and emits one uppercase hexadecimal string; empty input emits an empty string. It also implements base64encode over the complete byte stream using the standard Base64 alphabet without line breaks; empty input emits an empty string. The base64decode filter concatenates the complete input string stream, decodes standard Base64, and emits bytes in order; empty input emits no bytes, and invalid data raises a VM exception. URL component filters apply UTF-8 percent encoding/decoding as described below; malformed escapes or decoded UTF-8 raise a VM exception. The htmlspecialchars and htmlspecialchars_decode text filters implement the fixed canonical entity mapping described below. The html_entity_decode filter decodes recognized named and numeric HTML character references per input string and preserves unrecognized references and decodes only once rather than recursively processing newly produced text; it does not sanitize markup. strip_tags removes complete comments and markup-like spans whose tag names begin with an ASCII letter; quotes protect embedded > in attributes. It preserves ordinary text such as 2 < 3 and unterminated candidates. Each pipe string value is processed independently, so markup is not carried across chunks. Script/style contents remain as text after surrounding tags are removed. This filter is not an HTML sanitizer or a security boundary. The VM also implements csvenode for pipe<string[]>, with the CSV record and escaping rules in section 3.2.1. The VM implements csvdecode per input string using the strict record grammar in section 3.2.2; malformed records raise a VM exception. The VM also implements parse_str per item with form-style decoding into map<string, string>, and number_format(spec) for pipe<decimal> using invariant-culture .NET decimal formatting. Other listed standard filters remain unimplemented. This draft also references uint32, BlowfishContext, and AESContext without defining their public type contracts. The examples below are conceptual and are not all executable with the current compiler.

1. Common Rules for Filters

1.1 Invocation syntax

All filters in this document are applied to a pipe<T> using the filter(NAME ...) form. 

// Full form
stdin
    | filter(utf8)
    | filter(lineSplit)
    | filter(trim)
    | stdout;

However, within a pipeline statement the keyword filter may be omitted, and the sugar syntax |: NAME ... can be used instead. 

// Short form (pipeline-only sugar)
stdin
    |: utf8
    |: lineSplit
    |: trim
    | stdout;

The following two snippets are equivalent: 

stdin
    | filter(utf8)
    | filter(json: User);

stdin
    |: utf8
    |: json: User;

Filters that require type parameters receive the type as a labeled argument: 

stdin
    |: utf8
    |: json: User
    | users;

1.2 Type notation

For simplicity, types are written in a compact form in this document. Examples:

  • pipe<string> – a pipe of strings
  • pipe<byte> – a pipe of bytes
  • pipe<T> – a pipe parameterized by type T

1.3 Side effects and exceptions

Filters may exhibit the following behaviors:

  • Consume the entire input pipe before producing output (e.g. sort, shuffle, zip)
  • Pass through only a subset of the input (e.g. if, startswith, contains)
  • Maintain internal state (e.g. ciphers with contexts like AESencrypt)

How errors are handled (exceptions vs returning Result<T>, etc.) may be described individually for each filter when relevant.

1.4 Namespaces

The root namespace of the standard library is aloe. Every standard filter belongs to a namespace under this root.

  • Namespace names are all lowercase, and segments are separated by ..
  • Examples: aloe.text, aloe.encoding, aloe.crypto.hash, etc.

This document assigns each filter a “canonical fully-qualified name” of the form aloe.xxx.yyy. How imports work or how these names can be shortened in actual code is defined in the language specification.

2. Text / Encoding

2.1 utf8

The VM implementation consumes the complete byte stream and emits one string. UTF-8 is decoded strictly across input chunk boundaries; empty input emits an empty string, and invalid byte sequences raise a VM exception.

Namespace / Signature

Namespace: aloe.encoding
filter utf8 : pipe<byte> -> pipe<string>

Decodes the input byte stream as UTF-8 and produces a stream of strings.

stdin
    |: utf8
    |: lineSplit
    | stdout;

2.2 lineSplit

Namespace / Signature

Namespace: aloe.text
filter lineSplit : pipe<string> -> pipe<string>

Splits string chunks at \n and emits one line per element. A preceding \r is removed, empty lines are preserved, and a non-empty final partial line is emitted when the input closes. A trailing line separator does not create an additional final empty line. 

stdin
    |: utf8
    |: lineSplit
    |: trim
    | stdout;

3. JSON / Data Transformation

3.1 json (decode)

Namespace / Signature

Namespace: aloe.json
filter json<T> : pipe<string> -> pipe<T>

Decodes each input string as one JSON object into a struct T whose fields are only int, bool, or string. JSON and field names match exactly with case sensitivity, and every field is required exactly once. Unknown, duplicate, or missing names, type mismatches, and malformed JSON fail the filter with the input item and, when available, member name in the error. Coercion and null are unsupported. Int fields accept neither fraction nor exponent notation. Arrays, nesting, enums, and classes are unsupported. At the call site, the type is passed as in source |: json: User | users;. 

stdin
    |: utf8
    |: json: User
    | users;    // pipe<User>

3.2 CSV: csvenode / csvdecode

3.2.1 csvenode

Namespace: aloe.csv
filter csvenode : pipe<string[]> -> pipe<string>

Encodes each string array as one CSV record without a trailing line terminator. Fields containing comma, double quote, CR, or LF are quoted, and embedded double quotes are doubled. Other field contents are preserved. An empty array produces an empty record, while a one-element array containing an empty string is emitted as "" so the two cases remain distinguishable.

3.2.2 csvdecode

Namespace: aloe.csv
filter csvdecode : pipe<string> -> pipe<string[]>

Parses each input string as one CSV record and emits its fields as a string array. Commas separate fields; a quoted field may contain commas, CR, LF, and escaped double quotes. A quote inside an unquoted field, an unterminated quoted field, or characters between a closing quote and the next comma are invalid and raise a VM exception. An empty input record decodes to an empty array; "" decodes to one empty field. Records are processed per pipe value and quoted fields do not span values. 

stdin
    |: utf8
    |: lineSplit
    |: csvdecode
    | rows;   // pipe<string[]>

4. Conditional / Ordering

4.1 if / elseif / else

These filters form a group that controls which elements pass through based on conditions. They are interpreted as a single composite filter.

Namespace / Signatures (conceptual)

Namespace: aloe.filter
filter if : pipe<T> -> pipe<T>
filter elseif : pipe<T> -> pipe<T>
filter else : pipe<T> -> pipe<T> 

users
    |: if:     .Age >= 20 and .Gender == Gender.Male
    |: elseif: .Age >= 13
    |: else
    | stdout;
  • if is the first conditional branch.
  • elseif is an additional branch that is valid only when it directly follows an if or another elseif.
  • else passes elements that did not match any previous condition.

4.2 switch

Namespace: aloe.filter
filter switch : pipe<T> -> pipe<T> (detailed specification to be added)

switch retrieves a key from each element and routes it to one of multiple branches based on that key. For now, only the name and rough role are reserved; the exact syntax (how to write case clauses, etc.) will be defined in the language specification.

4.3 sort

Accepted decision 0026 also implements argument-free sort : pipe<string> -> pipe<string>. It buffers through input closure and emits the original strings in stable ascending ordinal UTF-16 code-unit order, independent of culture. Duplicate values, exact contents and normalization forms are preserved; the empty string sorts first. Empty input emits no values and output observes bounded backpressure. No key argument, case folding or normalization is applied.

The VM implements argument-free sort : pipe<int> -> pipe<int>, rejecting values outside signed int32. Under decisions 0025 and 0030, sort: .Field accepts an exact, direct, case-sensitive int or string field of a declared struct. It buffers the complete input until closure and emits original records in stable ascending order: signed int32 for int keys, ordinal UTF-16 code units for string keys. Duplicate records and source order among ties are retained. String contents and normalization forms are preserved without case folding or culture settings. Empty input closes the output without values. Bounded output respects backpressure; buffer memory grows with input count. Other key types, nested paths and key expressions are rejected.

Keyed AloeBC schemas retain the legacy three properties typeName, fieldName and fieldIndex for int keys. Optional fieldType accepts exactly int or string; the compiler adds fieldType:string for string keys. Invalid schemas and mismatched record/key values are rejected.

Namespace / Signature

Namespace: aloe.collection
filter sort : pipe<T> -> pipe<T>
filter sort(key) : pipe<T> -> pipe<T>

Sorts the input elements and emits them in sorted order. Internally, the filter buffers all elements, sorts them, and then outputs them. 

users
    |: sort: .Age   // sort by Age ascending
    | stdout;

4.4 shuffle

The current VM implements argument-free shuffle : pipe<int> -> pipe<int> under accepted decision 0023. It buffers the complete input until closure, applies Fisher-Yates using the noncryptographic System.Random.Shared source, and emits the full permutation under output backpressure. Counts and duplicates are preserved; empty input closes without values. Unchanged order is valid. No seed, deterministic replay, random-state persistence, or cryptographic unpredictability is promised. Accepted decision 0028 extends the same algorithm to pipe<string>, preserving exact original string contents, counts and duplicates without normalization or conversion. Other element types and arguments are rejected. Memory grows with input count and the buffer is released on completion. Each shuffle swap yields to the cooperative scheduler; bounded pipes do not bound the aggregate buffer. Do not use this filter to generate secrets.

Namespace: aloe.collection
filter shuffle : pipe<T> -> pipe<T>

Randomly permutes the order of elements. Internally, it buffers all elements and then outputs them in randomized order. 

cards
    |: shuffle
    | gameDeck;

5. Crypto / Hash / Binary

5.1 Hash: md4 / sha1 / sha256

The VM implements md4, sha1, and sha256 for pipe<byte>. Each filter consumes input incrementally without retaining the complete stream, waits for input closure before emitting the digest, then emits digest bytes in order (16 bytes for MD4, 20 for SHA-1, and 32 for SHA-256). Empty input emits the standard digest of an empty message. MD4 and SHA-1 are provided only for legacy interoperability and are unsuitable for new security-sensitive applications; prefer SHA-256 for new uses.

Namespace: aloe.crypto.hash
filter md4 : pipe<byte> -> pipe<byte>
filter sha1 : pipe<byte> -> pipe<byte>
filter sha256 : pipe<byte> -> pipe<byte>

Computes a hash value for the entire input and outputs the hash as a byte stream. For new security-sensitive hash applications, prefer sha256 or another profile-approved modern algorithm. md4 is a legacy-only option and was moved to Historic status by RFC 6150. NIST is transitioning away from SHA-1 for cryptographic protection by December 31, 2030; treat sha1 as a legacy/compatibility option for new applications (NIST transition plan). 

stdin
    |: sha256
    |: bin2hex
    | stdout;

5.2 Byte-level conversion: bin2hex / crc32

5.2.1 bin2hex

Namespace: aloe.encoding
filter bin2hex : pipe<byte> -> pipe<string>

Consumes the byte stream and emits one uppercase hexadecimal string. Empty input emits an empty string.

5.2.2 crc32

Namespace: aloe.crypto.hash
filter crc32 : pipe<byte> -> pipe<uint32>

Computes the CRC32 of the entire input and outputs it as a single integer.

5.3 Base64 / URL

The implemented URL filters use RFC 3986 URI-component rules: UTF-8 bytes outside the unreserved set A-Z a-z 0-9 - . _ ~ are encoded as uppercase %HH escapes. Spaces encode as %20; plus signs are literal and are not form-urlencoded spaces. Decoding rejects malformed escapes and invalid UTF-8.

The implemented encoder consumes the complete byte stream and emits one standard Base64 string without line breaks. The decoder concatenates the complete string stream, decodes it, and emits bytes in order. Empty input encodes as an empty string and decodes to no bytes; invalid encoded data raises a VM exception.

The implemented base64encode filter consumes the complete byte stream and emits one standard Base64 string without line breaks. Empty input emits an empty string.

Namespace: aloe.encoding
filter base64encode : pipe<byte> -> pipe<string>
filter base64decode : pipe<string> -> pipe<byte>

Namespace: aloe.net.http
filter urlencode : pipe<string> -> pipe<string>
filter urldecode : pipe<string> -> pipe<string> 

fileBytes
    |: base64encode
    | stdout;

// ...

stdin
    |: base64decode
    | fileBytes;

5.4 Symmetric cryptography: Blowfish / AES

5.4.1 Blowfish: blowfishencrypt / blowfishdecrypt

Namespace: aloe.crypto.cipher
filter blowfishencrypt(ctx: BlowfishContext) : pipe<byte> -> pipe<byte>
filter blowfishdecrypt(ctx: BlowfishContext) : pipe<byte> -> pipe<byte>

Uses a BlowfishContext containing key, IV, mode, etc., to perform encryption and decryption.

5.4.2 AES: AESencrypt / AESdecrypt

Namespace: aloe.crypto.cipher
filter AESencrypt(ctx: AESContext) : pipe<byte> -> pipe<byte>
filter AESdecrypt(ctx: AESContext) : pipe<byte> -> pipe<byte>

Performs encryption/decryption using AES (e.g. CBC / GCM). Supported modes and padding details are defined by AESContext.

6. String Utilities

6.1 Case conversion: tolower / toupper

Namespace: aloe.text
filter tolower : pipe<string> -> pipe<string>
filter toupper : pipe<string> -> pipe<string> 

lines
    |: tolower
    | normalized;

6.2 Case styles: camelcase / pascalcase / snakecase

Namespace: aloe.text
filter camelcase : pipe<string> -> pipe<string>
filter pascalcase : pipe<string> -> pipe<string>
filter snakecase : pipe<string> -> pipe<string>

  • camelcase: "hello world" → "helloWorld"
  • pascalcase: "hello world" → "HelloWorld"
  • snakecase: "Hello World" → "hello_world"

Words are separated by Unicode whitespace; repeated or leading/trailing whitespace is ignored. Each word is normalized with invariant casing.

6.3 Substring filters: startswith / contains / strstr

Namespace: aloe.text
filter startswith(prefix: string) : pipe<string> -> pipe<string>
filter contains(needle: string) : pipe<string> -> pipe<string>
filter strstr(needle: string) : pipe<string> -> pipe<string>

  • startswith: passes only lines that start with prefix, compared ordinally.
  • contains: passes only lines that contain needle, compared ordinally.
  • strstr: passes only lines containing needle and returns the substring from its first occurrence to the end (similar to PHP’s strstr); matching is ordinal.
lines
    |: startswith: "[ERROR]"
    |: strstr: "detail="
    | stdout;

6.4 Trimming / Joining: ltrim / rtrim / trim / join

Namespace: aloe.text
filter ltrim : pipe<string> -> pipe<string>
filter rtrim : pipe<string> -> pipe<string>
filter trim : pipe<string> -> pipe<string>
filter join(sep: string) : pipe<string> -> pipe<string>

ltrim, rtrim, and trim remove Unicode whitespace from the beginning, end, or both ends of each input string.

join concatenates all input strings using sep and outputs a single string. Empty input produces one empty string. 

lines
    |: trim
    |: join: "\n"
    | text;

8. HTML / Sanitization

8.1 Escaping / Unescaping

The VM implements htmlspecialchars by escaping &, <, >, ", and ' as &amp;, &lt;, &gt;, &quot;, and &#39;. htmlspecialchars_decode reverses only those canonical spellings, replacing &amp; last so nested text is not decoded twice. These filters escape text characters; they do not sanitize HTML markup. The html_entity_decode filter decodes recognized named and numeric HTML character references per input string and preserves unrecognized references and decodes only once rather than recursively processing newly produced text; it does not sanitize markup. strip_tags removes complete comments and markup-like spans whose tag names begin with an ASCII letter; quotes protect embedded > in attributes. It preserves ordinary text such as 2 < 3 and unterminated candidates. Each pipe string value is processed independently, so markup is not carried across chunks. Script/style contents remain as text after surrounding tags are removed. This filter is not an HTML sanitizer or a security boundary.

Namespace: aloe.html
filter htmlspecialchars : pipe<string> -> pipe<string>
filter htmlspecialchars_decode : pipe<string> -> pipe<string>
filter html_entity_decode : pipe<string> -> pipe<string>
filter strip_tags : pipe<string> -> pipe<string>

  • htmlspecialchars: converts characters like <, >, &, " to HTML-safe entities.
  • htmlspecialchars_decode: inverse of the above.
  • html_entity_decode: decodes a wider range of HTML entities (e.g. &nbsp;).
  • strip_tags: removes complete comment and markup-like spans from each string value; it does not sanitize the remaining text.
htmlLines
    |: strip_tags
    |: trim
    | plainText;

9. Parsing / Formatting

9.1 Query strings: parse_str

Namespace: aloe.net.http
filter parse_str : pipe<string> -> pipe<map<string, string>>

Parses one query string per input item and emits a map. Pairs are separated by &; the first = separates key and value, and a pair without = has an empty value. Empty segments are ignored; empty keys are allowed; duplicate keys keep their last value. Components use form-style decoding (+ is a space and %HH bytes decode as strict UTF-8). Malformed escapes or invalid UTF-8 raise a VM exception. Empty input emits an empty map. This behavior is distinct from the RFC 3986 urldecode filter, which preserves literal plus signs.

9.2 Number formatting: number_format

Namespace: aloe.number
filter number_format(spec: string) : pipe<decimal> -> pipe<string>

Formats each decimal value as a string. The format string spec is implementation-dependent; for example, "#,##0.00" can be used. The current VM uses .NET decimal custom numeric format strings with invariant culture; an invalid format raises a VM exception. The pipeline preserves item order and applies normal bounded-output backpressure.

9.3 Regex escaping: quote_meta

Namespace: aloe.text
filter quote_meta : pipe<string> -> pipe<string>

Escapes regular-expression meta characters so that the string can be safely used as a literal pattern. This filter is implemented for pipe<string>. 

patterns
    |: quote_meta
    | safePatterns;

Filters not listed in this document can be freely added by users or external libraries. The names defined here are reserved as “Aloe standard filters” and are intended to serve as a common API across compatible implementations.
