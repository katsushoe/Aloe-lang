0. Overview

AloeVM is a stack-based virtual machine designed for executing the Aloe language.
This document defines:

  • Execution model (stack machine / frame structure)
  • VM-level value model (primitives, structs, classes, enums, pipe/filter, etc.)
  • Heap and memory management policy
  • Representation of pipes / filters on the VM
  • AloeBC (Aloe bytecode) binary format
  • Policy for mapping to WebAssembly (WASM)
AloeVM assumes two runtime implementations:
  • C# implementation (VM running on .NET)
  • WASM-native implementation (code compiled directly to WASM by aloe2wasm)
This specification primarily defines the behavior of “C# VM implementation + AloeBC”.
For WASM, the policy is to “map the instruction set almost 1:1” and “delegate GC to the WASM runtime”.

1. Execution model

1.1 Stack machine model

  • The VM is a stack machine centered around an operand stack.
  • Arithmetic and comparison instructions take values from the top of the stack and push the result back.
  • Local variables and arguments are stored in a per-frame local area.

1.2 Execution unit

  • The execution unit is a function / method invocation. Synchronous calls execute immediately on the current VMThread.
  • A public async method invocation from another Object is enqueued in the target Object's CallBuffer and executed by the Scheduler on the VMThread Pool.
  • A self call executes synchronously when runtime identity satisfies targetObject == currentObject.
  • main() is a special Root / Tick Driver rather than an ordinary method and is not executed through CallBuffer.
  • Each function is registered in the AloeBC function table with code offset, local count, argument count, exception-handler references, and related metadata.

1.3 Exception handling model

  • Aloe’s try / catch / finally is lowered to an exception handler table at the VM level.
  • Exceptions are treated as object references in the VM, and the stack is unwound when an exception is thrown.
  • In the WASM implementation, exceptions are mapped to the host’s exception model or to a combination of multi-value returns and error codes.
    The format of the exception handler table is defined in section 6.6.

1.4 Execution modes

  • VM execution mode:
    • The C# VM implementation directly loads AloeBC and interprets or JIT-compiles the instructions.
  • WASM-native mode:
    • aloe2wasm converts AloeVM instruction sequences almost 1:1 into WASM instructions and AloeVM itself does not exist.
    • GC and low-level memory management are delegated to the WASM runtime.

2. VM value model

2.1 Categories of VM values

Conceptually, values handled on the VM are divided into the following categories.

Category Examples Notes
Integer (int32) int, enum, bitfield enum 32-bit signed integer. Enums are always int-based.
Other integers byte May be packed and treated internally as int32.
Floating-point float 32-bit IEEE754.
decimal decimal 128-bit approximate representation with precision comparable to C# decimal (implementation-dependent).
bool bool Internally 1 byte or int32. Comparison instructions may reuse those for int.
char char Unicode code point (implementation can use UTF-16 or UTF-32).
Object reference class instances, string Handle to a heap object (e.g., 64-bit ID).
Struct struct On the VM it is treated as a “blob of value” and always handled as an inline value (no common boxed heap object).
pipe pipe<T> Has a dedicated VM tag. Implementation may use OS pipes / sockets, etc.
filter filter Foo Has a dedicated VM tag. Wrapper of function and connection information.
enum / bitfield enum are represented as int32 on the VM.
bitfield enums are limited to 0–31 bits (maximum 32 bits).

2.2 AloeObject and heap objects

In the C# VM implementation, heap objects are identified by an object ID (e.g., a 64-bit integer).

  • Objects as values in the VM:
    • On the stack or in locals, only an objectId: long (an AloeObject) is stored.
  • The memory manager maintains the mapping from object ID to metadata, including:
    • Field list (reference slot definitions) for classes/structs
    • Value slots per field (primitive values or other object IDs)
    • Final field layout after trait composition
  • Structs can be handled under the same framework:
    • A struct instance is always placed inline as part of a parent object / array / stack frame.
    • From the VM’s perspective, a struct itself is never managed as an AloeObject on the heap and boxing is not performed.
    • Classes/arrays that contain structs are AloeObjects placed on slots as usual.

2.3 VM tags for pipe / filter

  • pipe<T> and filter use dedicated VM value tags distinct from class instances.
  • For easier WASM mapping, the internal representation should be structured so that it can be mapped to WASM “ref types” (e.g., externref / funcref / anyref).
  • A pipe holds information such as “tail buffer + reference to synchronization objects”, and a filter holds “bound handler function + in/out metadata”, etc.

2.4 Struct layout and alignment

Structs are always treated as inline values on the VM, and their memory layout follows the rules below.

  • Default layout (no @StructLayout or @StructLayout(Sequential)):
    • Fields are laid out in the same order as declared in source.
    • The starting offset of each field is aligned to an 8-byte boundary from the beginning of the struct. Padding bytes are inserted as needed after the previous field.
    • The total struct size may also be padded to a multiple of 8 bytes.
  • Explicit layout (@StructLayout(Explicit) + @FieldOffset annotations):
    • Each field is given a @FieldOffset(n) annotation specifying the offset (in bytes) from the beginning of the struct.
    • The VM places fields at the specified offsets. Overlapping fields (union-like usage) are allowed, but whether unintended overlaps are an error or undefined behavior is defined by the language specification.
  • Auto layout (@StructLayout(Auto)):
    • The VM is free to reorder fields and insert padding for optimization.
    • In this case, byte offsets are not considered a stable ABI; user code must not rely on them via sizeof or pointer arithmetic.
  • Arrays of structs:
    • Array elements are placed contiguously with struct-size stride. An array with N elements occupies N × sizeof(Struct) bytes of continuous memory.
    • This layout allows bulk operations (e.g., memcpy) on large numbers of structs such as 3D vectors.
Structs do not implement interfaces and are treated as simple value types that are not subject to virtual dispatch from the VM’s point of view.
Method calls are represented as “normal functions taking the struct as an argument”, so there is no calling convention that relies on boxing.

3. Call stack and frames

3.1 Frame structure

Each function call creates a frame, which contains at least the following:

  • Return address (PC of the next instruction to execute)
  • Link to the previous frame
  • Local variable area
  • Arguments area
  • Temporary value slots (if needed)

3.2 Calling convention (overview)

  • Call instructions (e.g., CALL) are executed with arguments already pushed on the stack.
  • After frame creation, arguments are moved to the local area (or left on the stack and accessed by index).
  • The return value is pushed as a single value on top of the stack.
  • Void functions do not push a return value.

3.3 Exception frames

  • Based on the exception handler table, the VM decides how far to unwind the stack.
  • After unwinding, control jumps to the beginning of the catch block and passes the exception object to a local or the stack.

4. Heap, references, and lifetime management (C# VM implementation)

4.1 Slot-based heap layout

  • A Heap Slot in the C# VM is fixed at 8 bytes and is the minimum allocation unit and placement boundary for heap storage within a Bank.
  • An Object's occupied size is its actual data size rounded up to an 8-byte boundary. For example, an Object containing 20 bytes of actual data occupies 3 Heap Slots = 24 bytes, leaving the final 4 bytes as padding / unused space.
  • The C# VM may manage the heap using size-class arenas such as 8 / 16 / 32 / 64 / 128 / 256 / 512 / 1024 bytes. A size class classifies Objects and is distinct from the Heap Slot size.
  • Each arena may be divided into Banks, which are the physical allocation and release units. A Bank is a contiguous region containing multiple Heap Slots.
  • Heap Objects are identified by ObjectId / Handle and occupy contiguous Heap Slots within a Bank. ObjectId / Handle is independent of the physical Bank / Heap Slot location.
  • Object starting positions within a Bank are always aligned to an 8-byte boundary. The Object table may represent physical location as a Bank plus Heap Slot index.
  • Exact Bank sizes, Heap Slot counts, and free-list structures are implementation details.
  • The Heap Slot defined in this section is distinct from local slots or value slots on the VM stack / call frame.

4.2 Object table and Runtime metadata

An Object table maps ObjectId to physical location and Runtime metadata.

  • Arena / slot position / object size / type metadata.
  • Committed State plus Dirty Member / Volatile Value metadata required by the current Tick.
  • Lifetime metadata including Reference Count, Reference Group Handle, Reference Dirty, and Destruction Candidate state.
  • In the current C# reference-VM prototype, class instance field values are kept as runtime metadata on the Object table entry. At least one physical Heap Slot (8 bytes) is reserved per field, and writes to Object Reference fields update the object's outgoing reference edges at the same time.
  • The prototype compiler lowers new Type(args) to Object allocation followed by a synchronous construct(...) call frame; the Object Reference is returned to the caller only after the constructor completes. this.field reads/writes inside constructors lower to internal Object-field runtime operations.
  • A reference to or management metadata for the Instance CallBuffer.
  • In the current C# reference VM class subset, Object field values and class type-name metadata are stored in the Object table entry as instance state / type metadata. Getter-only public properties and private/protected instance methods execute synchronously as ordinary VM call frames, receiving the implicit this Object Reference as their first argument. No external instance-property setter is generated. Public async methods / CallBuffer execution remain a later implementation milestone.

4.3 Reference Counting and Reference Groups

  • Reference Counting is the basic lifetime mechanism for Object References.
  • A Strongly Connected Component in the Object Reference Graph is a Reference Group with a unique Group Handle.
  • References between Objects inside the same Reference Group do not count as External References keeping the Group alive.
  • References entering a Group member from outside the Group are counted as Group External References.
  • A Group whose External Reference Count reaches 0 becomes a Destruction Candidate.
  • Per-Object Reference Count data may also be retained for Group split / dissolve, debugging, and reference recalculation.

4.4 Committed / Volatile lifetime of Reference members

  • Object Reference members follow the same Committed / Volatile rules as other members.
  • If a Reference member changes during a Tick, the owner Object sees the Volatile Reference while external Properties continue to observe the Committed Reference until Tick end.
  • When Committed Reference and Volatile Reference differ, both referenced Objects remain alive until Tick end.
  • After Tick Commit, the Volatile Reference becomes the new Committed Reference and the old Committed Reference is released.

4.5 Reference Graph / Group updates

  • Reference Graph and Reference Group maintenance is normally performed at Tick boundaries.
  • An Object / Group whose reference-typed members changed may be marked Reference Dirty.
  • Tick-end processing may prioritize Dirty regions; a full SCC analysis of the entire Object Graph on every Tick is not required.
  • A new edge may merge SCCs into one Group, while removing an edge may split a Group.
  • Detailed treatment of Object References stored indirectly through Array / List / Map / struct remains an open issue.

4.6 Destruction Candidates and Runtime Temporary References

  • An Object / Reference Group whose Reference Count reaches 0 is not freed immediately; it is first marked as a Destruction Candidate.
  • Destruction occurs after safety checks during Tick-end processing, including Runtime Temporary References and CallBuffer state.
  • A CallBuffer target Object and Object Reference arguments are Strong References until Call completion.
  • Object References on the VM stack, running method arguments, CallBuffer entries, and Volatile References are Runtime Temporary References considered by lifetime calculation.
  • Weak References are not part of the initial specification.

4.7 Bank placement and evacuation

  • Object allocation uses arena / Bank / slot storage selected by size class.
  • Objects belonging to the same Reference Group should, where practical, be placed in the same Bank or in a small number of Banks. This is a placement policy for improving Group-level reclamation and locality; a Reference Group is still allowed to span multiple Banks.
  • If every Object in a Bank is reclaimable and no Runtime Temporary Reference or CallBuffer Strong Reference keeps any Object in that Bank alive, the Bank may become a FreeBlock candidate without freeing its slots individually.
  • If a low-occupancy Bank is retained only by a small number of live Objects, those Objects may be evacuated to available slots in another Bank so that the source Bank becomes empty and can be released as a whole.
  • ObjectId / Handle remains unchanged across movement. Moving an Object updates only its Bank / slot location in the Object table, so references in other Objects or on VM stacks do not require bulk rewriting.
  • A high-occupancy Bank may be retained as-is or compacted in place instead of being evacuated.
  • Physical-memory optimizations must not change observable Committed / Volatile State or Reference lifetime semantics.

4.8 Three GC phases

The C# VM GC is divided into the following three phases at Tick boundaries.

  1. Plan phase
    • Inspect Reference Groups, External References, Runtime Temporary References, Destruction Candidates, and Bank occupancy.
    • Select sweep targets, evacuation source Banks, destination Banks, and FreeBlock candidates.
    • The planner may prioritize plans that reclaim more Banks or bytes for less movement.
    • The Plan phase normally does not change physical Object locations.
  2. Sweep / Move phase
    • According to the Plan, mark dead slots Available and move required live Objects to other Banks.
    • Update the Object table physical location after each Object move.
    • When the Tick movement budget is exhausted, Move processing may stop and the unfinished Plan may continue on a later Tick.
  3. FreeBlock phase
    • After Sweep / Move, detach Banks / backing blocks containing no live Objects from the allocator and return their physical memory as a whole.
    • A Bank that still contains any live Object must not be freed as a block.

4.9 Per-Tick GC budgets

  • GC must not move an unbounded amount of memory in a single Tick. Sweep / Move must have a finite per-Tick movement budget.
  • At minimum, either the number of moved Objects or the number of moved bytes is limited; an implementation may limit both.
  • For example, an implementation may cap movement at 256 Objects per Tick, but the concrete limits are implementation- and runtime-configuration-dependent.
  • The Plan phase may also use a budget such as scanned Banks, processed Objects, or elapsed work so that a large heap is not fully rescanned every Tick.
  • Evacuation may span multiple Ticks when a budget is reached. Handles for Objects already moved must remain valid during such intermediate states.
  • Releasing a completely dead Bank without moving Objects does not consume the Object movement budget.

4.10 Memory management in the WASM implementation

A WASM-native implementation may delegate physical GC / allocation to the WASM execution environment.
It must still preserve Aloe's observable Object ownership, Committed / Volatile State, Strong References held by CallBuffers, and Tick-boundary reference/lifetime semantics.

5. VM representation of pipes / filters

5.1 pipe<T>

  • Represented as a value with a dedicated PIPE tag at the VM level.
  • Internally, it is assumed to hold:
    • A buffer (ring buffer / queue)
    • Synchronization primitives (locks / condition variables, etc.)
    • Type information for the elements (reference to runtime type info)
  • The implementation must be thread-safe so that multiple threads can access it without corruption.
  • Possible implementations:
    • OS pipes / sockets
    • Ring buffers on memory-mapped files

5.2 filter

  • A filter is represented as a value with a dedicated FILTER tag.
  • Conceptually, a filter value is a struct containing:
    • A pointer to a bound function
    • Metadata of in/out types
  • User-defined filters can be represented using the same mechanism.

5.3 Execution model of pipeline statements


A | filter(F) | B;
  • The VM expands this statement into a sequence of “connection construction instructions”.
  • A typical flow:
    • Resolve the output pipe of A.
    • Create an instance of filter(F) and start bound(input, output) as a separate task/thread.
    • Connect the output pipe to B.
  • Implementations may optimize by executing multiple filters sequentially on a single thread.

5.4 Pipe lifecycle and VM instructions

Pipes are treated at the VM level as having roughly four lifecycle phases: creation → connection → disconnection → deletion. Each phase is manipulated by instructions in the “pipe / filter / connection category (category ID = 0x0A)”.

  • Creation phase
    • Allocate a new pipe instance and initialize its buffer and synchronization objects.
    • Representative instruction (example):
      • PIPE_NEW:
        • Takes element-type ID, buffer size, option flags, etc. as operands.
        • Pushes a pipe handle (PIPE-tagged VM value) on the stack as the result.
  • Connection phase
    • Connect producers / consumers / filters to an existing pipe.
    • Representative instructions (examples):
      • PIPE_BIND_PRODUCER:
        • Binds a producer-side endpoint (method/task) to a pipe handle.
      • PIPE_BIND_CONSUMER:
        • Binds a consumer-side endpoint to a pipe handle.
      • PIPE_CONNECT:
        • May be defined as a high-level instruction that connects multiple pipes and filters together as a pipeline.
  • Disconnection phase
    • Detach producers / consumers / filters from a pipe and stop new data from flowing in or out.
    • Representative instruction (example):
      • PIPE_DISCONNECT:
        • Detaches a specified endpoint from a pipe.
        • How to handle data still present in the buffer (discard or drain) is an implementation policy.
  • Deletion phase (Delete / Close)
    • Close the pipe and release related buffers and synchronization objects.
    • Representative instruction (example):
      • PIPE_CLOSE:
        • Closes a pipe handle; once it becomes unreachable from the GC’s point of view, the heap object for the pipe becomes a candidate for reclamation.
    • Language-level delete and implicit closes at the end of with blocks are compiled to these instructions.
Code acting as producer / consumer is typically expressed as a combination of “normal function/method + thread (or task)”.
If needed, control-only instructions like PRODUCER_START, PRODUCER_STOP, CONSUMER_START, CONSUMER_STOP may be added in category 0x0A.

5.5 Cooperative scheduler of the C# reference VM

  • The C# reference VM runs main and every bound filter as separate execution contexts inside a single VM thread. Each context owns its call frames and evaluation stack, which are saved and restored when the context is switched.
  • Runnable contexts are kept in a FIFO queue. A context runs for at most a fixed instruction quantum (currently 1024 instructions) and is then re-queued at the tail. A context is never queued twice.
  • A write to a full bounded pipe suspends the writer until a reader removes a value or the pipe is closed. A read from an empty, open pipe suspends the reader until a value arrives or the pipe is closed.
  • Returning from the outermost frame of a context completes only that context. It does not stop other contexts. The value left by main is the program result.
  • If no context is runnable while some context is still unfinished, the VM reports Pipe scheduler deadlock with the number of stalled contexts and the number of blocked readers / writers.
  • Property getters and the instance calls drained by tick() run synchronously inside a single SYSCALL and cannot be suspended. A pipe operation that would block inside such a call is a VM error. Non-blocking pipe operations are allowed there.
  • Frame locals and evaluation-stack values of suspended contexts are GC roots.

6. AloeBC binary format

6.1 Overall structure

AloeBC (Aloe Byte Code) is a binary format that stores compile results for AloeVM.

6.2 Header

Offset Size Field Contents
0 6 bytes Magic ASCII string "ALOEBC"
6 1 byte VersionMajor Major version
7 1 byte VersionMinor Minor version
8 1 byte VersionBuild Build number
9 1 byte Reserved Reserved (fixed 0)
10 4 bytes HeaderSize Total size of the header (little-endian)
14 4 bytes ConstPoolOffset Offset to the constant pool
18 4 bytes TypeTableOffset Offset to the type table
22 4 bytes FuncTableOffset Offset to the function table

The assumed endianness is little-endian.

6.3 Constant pool (overview)

  • Manages string literals, numeric literals, type information, etc. in a centralized pool.
  • Each entry is a variable-length record composed of “tag + length + body”.
  • Example tags:
    • 0x01: UTF-8 string
    • 0x02: int32
    • 0x03: float32
    • 0x04: decimal

6.4 Type table

AloeBC uses a unified TypeId space for primitive, compound, and function types. Instructions and function signatures should refer to types through TypeId wherever practical.

  • Every Aloe type (primitive / class / struct / enum / bitfield enum / pipe<T> / function type, etc.) is assigned a TypeId.
  • pipe<T> is represented as a compound type containing the element TypeId, rather than as an unparameterized PIPE tag. Therefore pipe<int> and pipe<string> are distinct types.
  • A function type stores its parameter TypeIds and an optional result TypeId; absence of a result represents void.
  • enum / bitfield enum use an int32 value representation at runtime while retaining their Aloe type identity through TypeId.
  • The number of valid bits for a bitfield enum (0–31) may be stored as metadata, for example to generate warnings.
The Type Table is the canonical type table for the entire AloeBC module, not merely a function-signature table. This allows the verifier to validate PIPE<T>, locals, parameters, and results in one TypeId space.

6.5 Function table and code section

  • Function table:
    • Function signatures (argument types, return type)
    • Number of local variables
    • Offset and length in the code section
    • Number of exception handler entries and offset to the first entry
  • Code section:
    • Stores VM instruction sequences as a byte array.
    • See chapter 7 for details on the instruction set.

6.6 Exception handler table

Each function has an associated table of zero or more exception handler entries. Using the information in the function table, one can obtain the relative offset and number of entries from the beginning of that function’s code.

Field name Type Contents
TryStartOffset uint32 Offset (in bytes) from the beginning of the function’s code. Start position (inclusive) of the try block.
TryEndOffset uint32 End position (exclusive) of the try block. The range is interpreted as [TryStartOffset, TryEndOffset).
HandlerStartOffset uint32 Start offset of the handler block (catch / finally / filter).
HandlerEndOffset uint32 End offset (exclusive) of the handler block.
HandlerKind uint8 Kind of handler. Example: 0 = catch, 1 = finally, 2 = filter (3+ reserved).

For finally this is fixed to 0; for filter its behavior is reserved for future extension.
  • If there are multiple catch blocks for a single try region, multiple entries with the same TryStartOffset / TryEndOffset and HandlerKind = catch are listed.
  • The order of evaluation of catch blocks follows the order in the table.
  • A finally block may have 0 or 1 entry for each try region.

6.7 AloeBC verifier

AloeVM validates AloeBC before executing function code. Once code has passed validation, the VM does not need to re-check types, local indexes, function indexes, or branch depths for every instruction (implementations may retain defensive checks).

  • Reject unknown opcodes and out-of-range constant, local, function, and TypeId references.
  • Reject operand-stack underflow and type mismatches. int32 and bool remain distinct validation types even if an implementation uses the same physical representation.
  • Validate correct nesting of BLOCK / LOOP / IF / ELSE / END.
  • Validate that BR / BR_IF depth refers to an active control frame.
  • Structured blocks in v0.1 do not produce result values. At normal block termination and at a branch, the operand-stack height must match the target control frame's entry height.
  • CALL pops parameter types and pushes the result type, if any, according to the callee function type.
  • pipe<T> instructions validate the element type. Writing an int32 to pipe<string>, for example, is a validation error.
  • Every reachable termination path of a non-void function must return a value of the declared result type.

After an unconditional BR or RET, the verifier may use a WebAssembly-like polymorphic stack for unreachable code. Structural validation of opcodes, indexes, and control nesting continues even in unreachable regions.

6.8 Validation errors and runtime traps

  • Validation error: type mismatch, stack underflow, invalid index, invalid branch depth, malformed control nesting, and similar structural errors. The module is rejected before execution.
  • Runtime trap / exception: division by zero, writing to a closed pipe, an invalid read from an empty pipe, host runtime failure, and similar state-dependent failures.

7. Instruction set and WASM mapping (overview)

7.1 Instruction categories

The instruction set is roughly divided into the following categories, with each category assigned a 1-byte category ID.

  • Stack operations
    • PUSH, POP, DUP, SWAP, etc.
  • Arithmetic / logical operations
    • ADD, SUB, MUL, DIV, MOD
    • AND, OR, XOR, SHL, SHR
  • Comparison operations
    • CMPEQ, CMPNE, CMPLT, CMPLE, CMPGT, CMPGE
  • Control flow
    • BLOCK, LOOP, IF, ELSE, END, BR, BR_IF
  • Function calls
    • CALL, RET
  • Object operations
    • NEWOBJ, GETFIELD, SETFIELD, etc.
  • Array / collection operations (future)
  • pipe / filter / producer / consumer / connection / disconnection
  • Exception handling / VM management / debugging instructions
This specification defines only the policies for instruction categories and ID composition.
Concrete opcode values and bit layouts for each instruction are defined in a separate document, “AloeVM Instruction Set Reference”.

7.2 Instruction ID structure (category + index)

Each AloeVM instruction is assigned a 16-bit (2-byte) instruction ID.
The ID is composed of the upper 1 byte as the category ID and the lower 1 byte as the index within the category.

  • 16-bit instruction ID structure:
    • Upper 8 bits: category ID (e.g., stack operations = 0x01, arithmetic = 0x02)
    • Lower 8 bits: index within that category (order in that category’s opcode table)
  • In formula form, the instruction ID is computed as: 
    OpcodeID = (Category << 8) | IndexInCategory
  • Examples:
    • 1st instruction in the stack operation category (category ID 0x01) → 0x0101
    • 2nd instruction in the same category → 0x0102
    • 3rd instruction in the arithmetic category (category ID 0x02) → 0x0203
Category ID (upper 1 byte) Category name (example) Notes
0x01 Stack operations PUSH, POP, DUP, SWAP, etc.
0x02 Arithmetic operations ADD, SUB, MUL, DIV, MOD, etc.
0x03 Logical / bitwise operations AND, OR, XOR, SHL, SHR, etc.
0x04 Comparison operations CMPEQ, CMPNE, CMPLT, CMPLE, CMPGT, CMPGE
0x05 Control flow BLOCK, LOOP, IF, ELSE, END, BR, BR_IF
0x06 Call / return CALL, RET, etc.
0x07 Memory access load/store for locals / arguments / globals / fields, etc.
0x08 Object / array operations NEWOBJ, NEWARR, GETFIELD, SETFIELD, etc.
0x09 Exception / error THROW, RETHROW, LEAVE, etc.
0x0A pipe / filter / connection Pipe creation / connection / disconnection / producer/consumer control, etc.
0x0B VM management / debugging NOP, HALT, BREAKPOINT, etc.
0xF0–0xFF Implementation-specific / experimental Reserved for extension instructions used only by specific implementations

7.3 Location of detailed instruction set

Concrete opcode IDs, operand formats, and binary encodings for individual instructions are not defined in this document, but in a separate document: “AloeVM Instruction Set Reference”.
Implementers should rely on the policies and category design described here, and consult the Instruction Set Reference for detailed definitions of the instruction set.

7.4 Structured control flow

AloeBC v0.1 uses WebAssembly-like structured control flow rather than arbitrary byte-offset jumps.

  • BLOCK / LOOP / IF create control labels and are closed by END.
  • ELSE corresponds to the nearest unfinished IF.
  • BR depth / BR_IF depth use an unsigned nesting depth rather than a byte offset. The innermost active control label has depth 0.
  • When the target of BR 0 is a LOOP, control returns to the beginning of the loop; for a BLOCK or IF, control continues after its matching END.
  • Arbitrary-address JMP / JMP_IF_* instructions are not part of the v0.1 core opcode set.

7.5 1:1 mapping policy to WASM

  • BLOCK, LOOP, IF, ELSE, END, BR, and BR_IF map directly to their WASM counterparts.
  • Basic arithmetic and comparison instructions are mapped as directly as possible to WASM instructions such as i32.add and i32.lt_s.
  • Exception handling is represented using the WASM exception-handling extension, or a combination of error codes and structured blocks.
  • pipe / filter are lowered through WASM ref types plus runtime / host functions.

7.6 Role of aloe2wasm

  • In addition to the path “Aloe source → AloeBC → AloeVM execution”, there is a separate
    • Aloe source → intermediate IR → WASM, providing a native WASM build path.
  • The closer AloeVM’s instruction set is to WASM’s, the simpler the compiler implementation becomes.
  • Ideally, we aim for a level where “serializing AloeVM instruction sequences directly as WASM” is nearly possible.

8. Object / Tick / CallBuffer execution model

AloeVM may execute async Commands on multiple VMThreads, but the ownership unit for Mutable State is an Object, not a Task. Another Object obtains state through public properties and requests state changes through public async methods.

8.1 Object ownership

  • A class Object owns its member state, and only that Object modifies it.
  • Another Object does not directly read or write class member variables.
  • Internal Tick changes update Volatile State while Committed State remains unchanged until Tick end.

8.2 public property and state visibility

  • An instance public property getter invoked from another Object reads the target Object's Committed State.
  • The owner Object reads its latest Volatile State, falling back to Committed State for members without a Volatile value.
  • An instance public property has no setter.

8.2.1 public static property

  • A public static property belongs to a type's static context rather than to an Object instance.
  • In TypeName.Property, TypeName is resolved as a type / static namespace rather than an Object Reference, so Object ownership and Volatile / Committed visibility rules do not apply.
  • Both getter and setter may be defined. Assignment TypeName.Property = value; invokes the setter synchronously and does not enqueue it in the Static CallBuffer.
  • Use a public static async method when an asynchronous static command is required.

8.3 Volatile State

  • Object-member writes update Volatile State directly during the Tick.
  • An implementation may avoid copying the complete Object State and instead use Dirty Member + Volatile Value with lazy copy.
  • The current C# reference-VM prototype stores Committed fields plus a dirty per-field Volatile overlay on each Object-table entry. Self/internal field reads in async methods prefer the dirty Volatile value, while an external public property query reads Committed State even during the same Tick.
  • When an Object Reference field changes during a Tick, both the old Committed Reference and the new Volatile Reference remain strong edges until Tick Commit, aligning Query visibility with GC liveness.
  • After the Instance CallBuffer reaches quiescence, tick() promotes dirty Volatile fields to Committed State, updates the Reference Graph, and only then returns to main.
  • After Tick Commit, Volatile State is discarded or reset.
  • The TaskChangeBuffer / Change Record model for field-change history is removed.

8.4 Instance CallBuffer

  • Each Object has a CallBuffer.
  • The current C# reference-VM prototype represents a public async instance-method invocation as a pending entry containing the target Object, function index, and argument values, and drains entries FIFO on a single VMThread inside tick(). Entries enqueued while draining are also processed in the same tick() until quiescence.
  • The target Object and Object Reference arguments of an unprocessed pending entry are protected from GC as Runtime Temporary Roots. This has the same liveness meaning as the future per-Object CallBuffer strong-reference metadata implementation.
  • A public async method call from another Object is enqueued instead of being executed immediately.
  • CallBuffer append is mutually exclusive and entries execute in recorded order.
  • A CallBuffer entry holds its target Object and Object Reference arguments as Strong References until Call completion.

8.5 CallBuffer ordering and determinism

  • CallBuffer locking establishes a call order for one execution and avoids data races.
  • If multiple VMThreads compete for the lock simultaneously, OS scheduling may change lock-acquisition order.
  • The current specification therefore guarantees Race Freedom, but not complete Replay Determinism for identical input.
  • Sender Object ID / Sender Sequence / Logical Call Order or similar rules for complete determinism are future work.

8.6 self calls and synchronous processing

  • A self call where targetObject == currentObject executes synchronously without entering CallBuffer.
  • Private / protected instance methods execute synchronously and may return values.
  • Ordinary functions and ordinary static methods execute synchronously and may return values.

8.7 Static CallBuffer

  • A public static async method uses a Static CallBuffer owned by its class / type.
  • Static async calls are also processed before the current Tick ends.
  • Which VMThread executes a Static CallBuffer and whether one type is always serialized remain open issues.

8.8 async CallGraph

  • Public async instance methods and public static async methods participate in CallGraph analysis.
  • An async-to-async call adds an edge, and every cycle including a self cycle is a Compile Error.
  • Dynamic dispatch contributes every statically reachable target; validation may be repeated at final link time.
  • SCC or an equivalent algorithm may be used for cycle detection.

8.9 Calls generated during a Tick

  • Calls present at Tick start and new async Calls enqueued while processing the Tick are all executed in the same Tick.
  • Ordinary CallBuffer entries are not carried into the next Tick.

8.10 Tick Quiescence

Running async method count == 0
AND
all Instance CallBuffers == empty
AND
all Static CallBuffers == empty
AND
Scheduler pending work == 0

The state above is Tick Quiescence. If a new Call is added, Quiescence has not been reached.

8.11 main() and tick()

  • main() is the one-time Root Scope / Tick Driver and is outside CallBuffer execution and Quiescence checks.
  • The set of Object References reachable directly or indirectly from main scope is the semantic Root.
  • tick() is callable only from main and may be implemented as a Runtime intrinsic or dedicated statement.
  • tick() is a synchronous Barrier; when it returns, async work, Volatile Commit, Reference Graph / Reference Group / Reference Count updates, and Destruction Candidate evaluation have completed. GC Plan / Sweep / Move / FreeBlock are separated from tick().
  • When main returns, the program terminates and remaining Object Graph / Reference Group / CallBuffer state may be destroyed.

8.12.1 Explicit GC Runtime intrinsics

  • GC.debug is a runtime-provided read/write public static property<bool> that may be read or changed from main. While true, the runtime emits GC diagnostics for Reference Graph / Plan / Sweep / Move / FreeBlock processing; false disables them. It is independent of VM instruction tracing and does not change liveness or GC budgets.
  • Where measurable, a GC work completion log includes elapsedMs, heapUsedBytes, and heapReservedBytes. The C# reference VM also reports managedBytes from System.GC.GetTotalMemory(false) as a host-memory reference value.
  • heapUsedBytes is the total byte size of fixed Aloe Heap slots occupied by live Objects; heapReservedBytes is the total capacity of all currently allocated Banks.
  • If GC debug became true at least once during a program run, the C# reference VM emits [PERF] Program end when execution completes. Program elapsedMs covers entry-point execution only and excludes compilation; gcElapsedMs is cumulative GC work time during the same run.
  • For Host managed-heap diagnosis, the [PERF] summary may report managedStartBytes / managedBytes / managedDeltaBytes, the Host managed allocation delta allocatedDeltaBytes for the same program run, and .NET GC collection-count deltas hostGcGen0 / hostGcGen1 / hostGcGen2. These are Host diagnostics independent of Aloe Heap liveness, and diagnostics must not force a Host GC collection.
  • A REPL implementation may route GC diagnostic output to the current REPL session output.
  • GC.require() is a Runtime intrinsic callable only from main. The VM refreshes Runtime Temporary References from the current stack / frame locals / CallBuffer state and advances one Plan / Sweep / Move / FreeBlock unit within the normal GC budget.
  • If GC.require() does not complete the Plan, the active Plan may continue in later GC work.
  • GC.finish() is a blocking Runtime intrinsic callable only from main. If an active GC Plan exists, it runs synchronously until that currently requested GC cycle reaches PlanCompleted. If no active GC Plan exists, it is a no-op and must not start a new Plan or GC cycle.
  • GC.finish() does not change Object / Reference Group liveness rules. To guarantee completion, an implementation may temporarily relax the normal moved-object / moved-byte budget only while this explicit operation is active.
  • The VM may initiate automatic GC equivalent to GC.require() at safe execution points in response to memory pressure or similar policy. The explicit API does not disable normal automatic reclamation.

8.13 VMThread Pool and scheduling

  • The VM may use multiple VMThreads / OS threads to execute async methods on different Objects in parallel.
  • Mutable State of one Object is modified only by methods executing as that Object's owner.
  • The Scheduler assigns pending CallBuffer work to the VMThread Pool and includes pending work in Tick Quiescence.

8.14 Separation from Game Frames

  • A VM Tick is not the same concept as a Game Render Frame.
  • The VM does not know Renderer / VSYNC / Frame Clear / GPU concepts.
  • A Host Runtime may use a flow such as Input processing → Aloe commands → tick() → Physics → Render.

8.15 Host synchronous Queries

  • Static methods such as Keyboard.isDown / isPressed may synchronously query Host state.
  • Because they may be called from multiple VMThreads, Host Thread Safety requirements must be specified separately.

8.16 async failure and Tick atomicity

A candidate rule is that an unhandled exception in an async method causes Tick Failure, joins running VMThreads, does not Commit Volatile State, discards unprocessed Calls, and throws from tick() to main. This remains open, including treatment of irreversible Host side effects.

9. Open issues / TODO

9.1 Undecided items

  1. Whether public property getters are restricted to side-effect-free read-only Queries.
  2. How shared state behind mutable globals / static fields and settable public static properties is synchronized across VMThreads.
  3. Thread Safety requirements for Host synchronous functions / Queries.
  4. Final constructor execution rules and prohibition of this escaping asynchronously before construction completes.
  5. Tick Failure / Volatile rollback / tick() exception propagation for unhandled async-method exceptions.
  6. Handling of unprocessed CallBuffer entries and irreversible Host side effects on Tick Failure.
  7. VMThread ownership and serialization rules for Static CallBuffer.
  8. Logical ordering for complete Replay Determinism.
  9. One-Tick latency from same-Tick Property visibility and whether Phase semantics are needed.
  10. Graph-edge rules for Object Reference properties and Object References stored in Collections.
  11. Reference Group merge / split / Dirty local SCC update algorithms.
  12. Visibility and lifetime of Objects created / destroyed during a Tick.
  13. Tick Atomicity for Host side effects such as Audio / Network / File / Renderer commands.
  14. Intra-Tick visibility of Pipe data.

9.2 Future extension candidates

  • JIT compilation layer (native code for hot functions).
  • Debugger hooks (breakpoints, step execution, variable watch).
  • Profiler API (measuring execution time and allocated memory).
  • Distributed execution (pipes across multiple processes/nodes).
Even with the current contents of this specification, the goal is to make it possible to implement an Aloe compiler, the C# AloeVM implementation, and an aloe2wasm prototype.
However, details of the instruction set and memory management are expected to be refined through experimentation.

Appendix: Editing policy for generative AI (not part of the specification body)

This appendix describes the rules for editing the AloeVM specification using a generative AI system (e.g., ChatGPT). It is not part of the main specification text, and it must never override the technical content of the specification.

  • Do not change the technical meaning or behavior of the specification. Fixing typos or unifying obvious notation inconsistencies is allowed, but algorithms or behavioral semantics must not be changed.
  • Do not change chapter structure or heading order unless explicitly instructed by the user.
  • Keep the logic of existing sample code or pseudo code; do not perform cosmetic changes such as arbitrary casing modifications that do not improve clarity.
  • Content explicitly stated to be “defined in another document” (e.g., instruction set details) must not be inlined into this specification. When more detail is needed, add only references such as “See the AloeVM Instruction Set Reference”.
  • When updating metadata, always update edit-version and edit-date in the header.
  • Handling of timestamps:
    • edit-date must always use the current time in the Asia/Tokyo time zone.
    • The format must be ISO 8601 (e.g., 2025-12-03T11:45:54+09:00) and include date, time, and timezone offset.
    • Do not guess or use a different timezone; generative AI must write the exact current time in Asia/Tokyo as provided by the user or by a dedicated tool.
  • This appendix itself may be extended or corrected when needed, but such changes must not affect the technical contents of the main specification.
