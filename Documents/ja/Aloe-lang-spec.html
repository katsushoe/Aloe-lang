Aloe 言語仕様書（ドラフト、日本語版）

edit-version: 159
edit-date: 2026-10-22T11:02:13+09:00

この文書は、英語版仕様をベースにした日本語ドラフトです。
本版では「欠如」を言語として認めない方針とし、null / valid / invalid / delete / capture を仕様から排除します。
オブジェクト破棄は GC に任せ、外部資源（ファイル等）は using / Dispose パターンで管理します（8章）。
with ブロックは target を 1 回だけ評価して保持し、.Member を target.Member に展開する省略記法として定義します（ロック/timeout/特別な例外扱いはありません）。
さらに、任意値の受け皿として object を導入し、 プリミティブ値は box object に boxing して保持し、unboxing は as / 暗黙 unbox キャスト により行います。
文字列型 string は 値型 として扱います（2.3.1）。
それ以外の仕様は原文にできるだけ忠実に訳しています。

0. Overview（概要）

Aloe は静的型付けのスクリプト言語であり、シンプルで直感的な構文を目指している。
スタックベースの仮想マシン（AloeVM）上で動作し、主に次のような目標を持つ。

  • 教育用途や小規模アプリケーションで読み書きしやすいこと
  • C# ランタイムおよび WebAssembly (WASM) 環境で動作すること
  • pipe と filter によって、I/O と並行処理を静的型付けのまま制御できること

特徴：

  • 静的型付け
    • var による型推論（初期化必須）
    • let による明示的な型指定（初期化必須）
  • 値型 / 参照型
    • struct ... 値型
    • class / object ... 参照型
    • string ... 値型（2.3.1）
  • GC ベースのメモリ管理（具体的なアルゴリズムは VM 実装依存）
  • 外部資源は using / Dispose パターンで管理する
    • using ブロック終了時に Dispose を確定的に呼ぶ（8章参照）。
    • Dispose 後のメンバーアクセスは ObjectDisposedException とする（8章参照）。
  • object と box object による boxing / unboxing
    • プリミティブ値（string を含む）を object に保持する場合、対応する box object に boxing される。
    • object からプリミティブを取り出す場合、as / 暗黙 unbox キャストを用いる。
    • 数値型同士の変換や文字列パースは as / 暗黙 unbox キャストでは行わず、標準ライブラリの Parse / TryParse を用いる。
  • pipe / filter によるデータフロースタイルの設計

1. Basic Syntax（基本文法）

1.1 Comments（コメント）

// single-line comment




/* multi-line
   comment */

struct Point { field x: int; field y: int; method sum(offset: int): int { return this.x + this.y + offset; } }
function measure(point: Point): int { return point.sum(1); }
  • // から行末までが行コメント。
  • /* ～ */ が複数行コメント。
  • 複数行コメントは、開始 /* から最初に現れる */ までを まるごとコメントとして扱う。 コメントの内部に追加の /* や */ が現れても、 それらはすべてコメントの一部として無視される（ネストしたコメントの構文解析は行わない）。
    したがって、コメント内の「コメント構文」が破綻していても、 いったん /* が始まってから最初の */ が来るまでは常にコメント扱いとなる。

1.2 Identifiers（識別子）

  • 使用可能文字：英字 (A-Z, a-z)、数字 (0-9)、アンダースコア _
  • 先頭文字は英字または _ でなければならない。
  • 大文字小文字は区別される。
  • キーワードと同じ綴りは使用できない。
  • _ 単独は識別子として使用できない。_name や foo_bar のように他の文字と組み合わせた識別子内のアンダースコアは使用できる。
  • ユニコード文字も使用できる（空白や区切り記号などは除外）。

1.4 Literals（リテラル）

  • 整数リテラル：10, 0, -5, 0x1A, 0b1010 など

  • マップリテラル：["key1": 10, "key2": 20]

1.5 Statement terminator（文の終端）

var x = 10;
x = x + 1;
print(x);
  • すべての文はセミコロン ; で終わる。
  • 改行による自動セミコロン挿入は行わない。

1.5.1 Function completion（関数の終了条件）

  • void 以外の関数では、通常終了できるすべての経路で値を返す必要がある。
  • リテラル条件が true の while ループに到達可能な break がない場合、そのループから通常終了できない。到達可能な break がある場合はループを抜けられるため、その後に続く経路では関数が値を返す必要がある。
  • ループ出口の解析では、到達不能な分岐にある break は考慮しない。たとえば if (false) 内の break は while (true) の通常終了経路にならない。

1.6 Whitespace（空白）

  • スペース、タブ、改行はトークン区切りとして扱われる。
  • 連続する空白は 1 つの区切りとみなされる。
  • インデントに意味はない（Python とは異なる）。

1.7 Case sensitivity（大文字小文字）

  • 識別子とキーワードは大文字小文字を区別する。
  • キーワードはすべて小文字（Result を除く）。

2. Type System（型システム）

2.1 Primitive types（プリミティブ型）

Aloe における「プリミティブ型」は、次の 8 種類とする。

  • bool / boolean - 真偽値。
  • int / integer - 符号付き整数。
  • float - 浮動小数点数。
  • decimal - 高精度 10 進数。
  • string - 文字列（値型。2.3.1 参照）。
  • byte - 0-255 の符号なし整数。
  • char - 1 文字。
  • void - 戻り値なし（戻り値専用）。

仕様書から null は排除する。

2.2 Composite / user-defined types（合成型 / ユーザー定義型）

  • 配列：T[]
  • リスト：T()
  • セット：T{}
  • マップ：map<T> または map<K/V>
  • struct
  • class
  • enum, bitfield enum
  • 非同期タスク：task
  • 万能参照型：object
  • パイプ：pipe<T>（18章参照）
  • 結果型：Result<T>（18章参照）

2.3 Value types / reference types（値型 / 参照型）

  • 値型：
    • int, float, decimal, bool, byte, char, string
    • struct
    • enum, bitfield enum（内部表現は int32）
  • 参照型：
    • class
    • object
    • task, pipe<T>, Result<T> など

2.3.1 string 値型の観測可能な意味（固定）

  • 代入は値コピーとして観測される。 実装は内部共有などの最適化を行ってよいが、その有無は仕様上観測できない。
  • string は不変（immutable）であり、既存の string の内容を書き換える操作は存在しない。連結や置換は新しい string を返す。
  • 比較演算子 == は内容比較である（参照比較ではない）。
  • 値型に対する破棄は言語仕様として持たない。
  • object へ代入する場合、string は常に String box object に boxing される（2.4参照）。

  • object は、void を除く任意の値を保持できる特別な参照型である。
  • 参照型の値は object へ暗黙に代入できる（参照コピー）。
  • プリミティブ値（string を含む）を object に代入する場合、対応する box object に boxing される（2.4参照）。

Struct restrictions and copying（struct の制約とコピー）

  • struct のフィールドにはプリミティブ型と他の struct のみを持てる。
  • class などの参照型フィールドは持てない。
  • struct の代入は常に値コピー。
  • 最大サイズなどは仕様で制限しない。

Class vs struct（class と struct）

  • class は struct をフィールドとして持てる。
  • class インスタンスを別変数に代入すると参照がコピーされる（オブジェクト本体は共有）。

Aloe は、プリミティブ値を object に格納するために、各プリミティブ型に対応する box object を定義する。
box object は object から派生し、名前は大文字で始まる英単語とする。

  • bool / boolean - Boolean
  • int / integer - Integer
  • float - Float
  • decimal - Decimal
  • string - String
  • byte - Byte
  • char - Char

2.4.0 boxing の正準規則（固定）

  • プリミティブ値（string を含む）を object に代入する場合、必ず対応する box object に boxing する。
  • box object を object に代入する場合は、その参照を保持する（再 boxing はしない）。
  • box object は対応する値を内部に保持するが、value プロパティは公開しない（value は非公開）。
  • unboxing は対応する ToXxx() メソッドで行う。
  • ToXxx の正準名は次の通り：
    • ToBool(), ToInt(), ToFloat(), ToDecimal(), ToString(), ToByte(), ToChar()
  • unboxing：object からプリミティブ値を得るには as（15.1）/ 暗黙 unbox キャスト（5.2.2）を用いる。

2.4.1 角（変換の禁止）

  • 型変換は行わない。 例えば数値型同士の変換や文字列のパースなどは、as / 暗黙 unbox キャストの範囲では行わない（失敗として扱う）。

2.4.2 Parse / TryParse（文字列から数値への導線）

数値型同士の変換や文字列パースは as では行わない。
文字列から数値への変換は、対応する box object が提供する Parse / TryParse を用いる。

  • Integer.Parse / Integer.TryParse（int）
  • Byte.Parse / Byte.TryParse（byte）
  • Float.Parse / Float.TryParse（float）
  • Decimal.Parse / Decimal.TryParse（decimal）
2.4.2.1 共通ルール（受け付ける文字列）
  • 入力は string とする。
  • 先頭と末尾の ASCII 空白（U+0020）およびタブ（U+0009）は無視してよい（実装は trim してよい）。
  • 文字列内部の空白は許可しない。
  • 桁区切り（カンマ等）は許可しない。
  • NaN / Infinity は概念として存在しないため、これらの表記は受け付けない。
  • 解析不能な場合は FormatException（Parse）または TryParse の失敗とする。
  • 表現可能範囲外の場合は OverflowException（Parse）または TryParse の失敗とする。
2.4.2.2 Integer / Byte の書式
  • 10進：[+|-]?[0-9]+
  • 16進：[+|-]?0x[0-9a-fA-F]+
  • 2進：[+|-]?0b[0-1]+
  • Byte は符号を許可しない（- を含む場合は失敗）。
  • Byte は 0..255 の範囲外を失敗とする。
2.4.2.3 Float の書式
  • 十進小数：[+|-]?([0-9]+(\.[0-9]*)?|\.[0-9]+)
  • 指数部（任意）：上記に続けて [e|E][+|-]?[0-9]+ を許可する。
  • オーバーフロー/アンダーフローは例外（Parse）または失敗（TryParse）とする（3.5参照）。
2.4.2.4 Decimal の書式
  • 十進小数：[+|-]?([0-9]+(\.[0-9]*)?|\.[0-9]+)
  • 指数表記は許可しない。
  • 精度・丸め・範囲は実装が持つ decimal 仕様に従うが、表現不能なら OverflowException（Parse）または失敗（TryParse）とする。
2.4.2.5 Parse と TryParse の戻り
  • Parse は成功時に値を返し、失敗時に例外を投げる。
  • TryParse は成功時に値を返し、失敗時に例外を投げない。
  • TryParse の失敗表現は、標準ライブラリが定義する仕様に従う（Result を用いる場合、ErrorMessage は必須である。18.2.1参照）。

3. Numbers & Conversions（数値と暗黙変換）

3.1 int and float

  • int と float を混在させた式の結果は float になる。
    • int + float -> float
    • int - float -> float
    • int * float -> float
    • int / float -> float

3.2 decimal

  • decimal は高精度な 10 進数。
  • int との混在式は decimal に昇格する。暗黙変換の精度規則を定めていないため、decimal と float の混在はコンパイルエラーとする。
  • 現行コンパイラーは decimal の +、-、*、/、% と数値比較をサポートする。int と混在する演算結果も decimal となる。
  • オーバーフロー / アンダーフロー / 精度問題は OverflowException として扱う。

3.3 enum and int

  • Aloe にはキャスト構文がない。
  • enum と int の暗黙 / 明示変換はいずれも禁止。
  • enum と数値型の混在式はコンパイルエラー（bitfield enum のビット演算を除く）。
  • 内部表現としては enum / bitfield enum はすべて int32。

3.4 byte and char

  • byte：
    • 範囲は 0-255。
    • byte 同士の演算は許されるが、範囲外はエラーになり得る。
    • byte と int の混在式は int に昇格。
  • char：
    • char の算術演算は不可。
    • 比較演算（==, <, > 等）は char 同士のみ。
    • 数値型との暗黙変換はない。

3.5 NaN / Infinity

  • NaN / Infinity は概念として存在しない。
  • 数値オーバーフロー/アンダーフローは NaN/Infinity ではなく例外で扱う。
  • ZeroDivisionException は 0 / 0.0 で常に投げる。

4. Blocks & Scope（ブロックとスコープ）

ブロックは { と } で区切られ、各ブロックが新しいスコープを導入する。

  • main ブロック
  • クラス定義ブロック
  • メソッド定義ブロック
  • 任意の { ... } ブロック
  • using ブロック（4.4参照）

4.1 Static (lexical) scope and shadowing（静的スコープとシャドウイング）

class Sample {
    field value: int = 1;
    method foo(): void {
        var value = 2;        // フィールドをシャドウ
        print(value);         // 2
        print(this.value);    // 1
    }
}
  • Aloe は静的（レキシカル）スコープ。
  • 内側ブロックで同名変数を宣言すると、外側の変数をシャドウする。
  • フィールド名とローカル変数名がぶつかった場合、ローカル変数が優先される。フィールドは this. で参照する。

4.2 with-blocks（メンバー省略記法）

Aloe には、同一オブジェクト（または同一値）のメンバーアクセスを簡潔に書くための with ブロックがある。
本版の with は 省略記法のみを提供し、ロック、timeout、例外の特別扱い等は行わない。 

with (user) {
    .name = "Alice";
    .age = .age + 1;
    print(.name);
}
  • with (target) { ... } ブロック内では：
    • .Member は (target).Member の省略形。
    • target はブロックの開始時に 1 度だけ評価され、内部で保持される（再評価しない）。
  • _ は特別扱いしない。 with 対象を表す暗黙変数は存在しない。
  • with は短絡安全アクセス（例：a?.b）を提供しない。

4.2.1 with 対象と評価（target を 1 回だけ評価して保持）

with (target) の target は式であり、ブロック開始時に 1 回だけ評価して保持する。
ブロック内の .Member は、保持した target へのメンバーアクセスに展開する。

4.2.1.1 target の評価回数（固定）
  • target 式は 1 回だけ評価される。
  • 評価結果は内部的に保持され、ブロック内で繰り返し利用される。
  • target 式を再評価する構文は存在しない。
4.2.1.2 target の型制約（プリミティブ禁止、構造体/コンテナ/参照型許可）
  • プリミティブ型（bool/int/float/decimal/string/byte/char/void）は target にできない。
  • struct は target にできる。
  • 配列/リスト/セット/マップ等のコンテナは target にできる。
  • class/object 等の参照型は target にできる。

プリミティブはプロパティ・メソッドを持たない前提であるため、with の対象から除外する。 struct やコンテナはメンバーを持ち得るため対象とする。

4.2.1.3 フィールドチェーン target の評価順（左から右）

target がフィールドチェーン（例：a.b.c）の場合、with は 左から右に評価する。
ただし、評価結果は最終的に「保持される target 値」として 1 つに確定する。

  • 評価は各段階で 1 度だけ行い、同じ段階を再評価しない。
4.2.1.4 ロック/timeout/特別な例外扱いは行わない（固定）
  • with はピン止め（ロック）を行わない。
  • timeout(...) は with の構文として存在しない。
  • with には catch を付ける特例はない（例外処理は通常の try/catch を用いる）。

4.2.2 Type-based with（class / struct / enum の static / 列挙子ショートカット）

通常の with (target) に加えて、型名 を対象にした with を利用できる。 

with (TypeName) {
    .SomeStaticMethod();
    .SomeStaticField = 1;
}

ここで TypeName は次のいずれか：

  • class 型
  • struct 型
  • enum / bitfield enum

この場合、with は「型コンテキスト with」として解釈される：

  • () 内の式は実行時に値として評価されない。
    • コンパイラは TypeName を型として解決し、インスタンス生成などは行わない。
  • ブロック内では：
    • .Member は TypeName.Member の省略形。
    • 型ベース with 内でインスタンスメンバーにアクセスすることはコンパイルエラー。

型ベース with も複数ターゲット構文に混在させられる。解決順序は左から右であり、曖昧ならコンパイルエラーとする。

4.3 名前解決の正式ルール（曖昧ならコンパイルエラー）

Aloe は「曖昧ならコンパイルエラー」を原則とし、名前解決の探索順を次のように固定する。 本節は、識別子（非修飾名）および型名の解決に適用される。

4.3.1 非修飾識別子（x）の探索順

  1. 現在のブロックのローカル変数 / 引数（最内側スコープから外側へ）
  2. （メソッド内の場合）同名のフィールド（暗黙 this スコープ）
  3. 同一 namespace 内のトップレベル宣言（関数 / 型 / 定数など）
  4. import により導入された名前（明示 import されたもの）
  5. 外側 namespace（親 namespace へ遡る）
  • 同一段階で複数候補が存在する場合は コンパイルエラー。
  • 型名と値名（変数名など）が同名で衝突し、構文から区別できない場合は コンパイルエラー。

4.3.2 メンバー名（obj.Member）の探索

  • obj.Member は、obj の静的型に基づき、該当するメンバーを解決する。
  • 継承がある場合、派生型から基底型方向へ探索する。
  • 同名候補が複数（オーバーロード等）で、引数型から一意に確定できない場合は コンパイルエラー。

4.3.3 with ブロック内の .Member

  • .Member は、最内側の with から外側へ、かつ同一 with 内では左から右の順で探索する（4.2参照）。
  • 複数ターゲットで解決が曖昧になる場合は コンパイルエラー。

4.4 using ブロック（Dispose の確定呼び出し）

using は、ブロック終了時に対象オブジェクトの Dispose() を確定的に呼び出す構文である。
using は外部資源（ファイル、ソケット等）の解放を目的とし、オブジェクト破棄（メモリ解放）を行うものではない。 

using (r = OpenReader("file.txt")) {
    var s = r.ReadLine();
    print(s);
}
// ブロック終了時に r.Dispose() が呼ばれる
  • using (x = E) { ... } の E は 1 回だけ評価され、結果が x に束縛される。
  • using ブロックを抜けるとき（正常終了・例外伝播のいずれでも）、x.Dispose() が 1 回だけ呼ばれる。
  • Dispose() の呼び出し順序は、ネストした using については内側から外側（LIFO）とする。
  • Dispose() が例外を投げた場合、その例外はブロック終了処理の例外として伝播する（集約の有無は実装依存）。

5.2.2 暗黙 unbox キャスト（非消費）

演算・条件式の暗黙unboxingプロトタイプ（2026-10-14）：算術、大小比較、primitive／参照の比較は型が一致するboxを非消費で取り出し、別名を変更しません。名前付きboxは自身のprimitive種別を使用し、型を限定しない参照は相手のprimitive／名前付きbox型、または固定された数値の期待結果型を使用します。型文脈のないopaque参照同士の数値演算は拒否します。明示asで型を指定してください。int専用のbit演算・shift・補数はopaque参照へint文脈を与えますが、名前付きByte等の非intは拒否します。取り出した後のbyte／int／float／decimal演算は既存の昇格規則を使います。取り出し自体は変換や文字列解析をせず、decimal／float混在も拒否します。if／while、not、and／orはbool文脈です。式を左から右へ一度ずつ評価し、左の取り出し失敗時は右の副作用を実行しません。短絡評価では選ばれない右式とcastを実行しません。名前付きboxを含む参照同士の==／!=はObjectId同一性比較を維持し、primitiveと参照の組み合わせでは値を取り出して比較します。invalidとの比較は有効性検査を維持します。無効・不一致boxは既存の暗黙asと同じInvalidCastExceptionで、元参照を保持します。配列／class／関数／GC root、Tick／getterの読み取り規則を維持します。String／Char／Booleanは対応済みのprimitive比較・論理演算だけに対応し、文字列連結や数値解析は追加しません。syscall／opcode／codec形式は変更せず、直接WASMのboxと実行時種別からの動的推論は未対応です。演算unboxingの設計判断（英語）を参照してください。以下の例はAloeBC往復後に42を返します。
function main(args: string[]): int {
    var number = new Integer(40);
    let increment: object = 2;
    var enabled = new Boolean(true);
    var alias = number;
    if (enabled and number == alias and number != invalid) {
        var total = number + increment;
        if (total == 42 and number == 40) { return total; }
    }
    return 0;
}

期待される型がプリミティブ型 P に固定できるコンテキストでは、 式 E に対して 暗黙 unbox キャスト を許可する。
暗黙 unbox キャストは 参照を消費しない。

暗黙 unbox キャストが許可される代表的なコンテキスト：

  • let x:P = E;（初期化）
  • x = E;（代入。x の型が P）
  • return E;（関数の戻り値型が P）
  • f(E)（引数型が P）
  • 暗黙 unbox キャストは、演算子型付け（例：E + 1 のため）には適用しない。 必要な場合は E as P を明示するか、一旦 let t:P = E; のように受ける。

暗黙 unbox キャストは意味的には E as P と等価であり、失敗時は InvalidCastException を投げる。 ifnot による代替値指定は、明示 as（15.1）でのみ行える。 

let o: object = 123;   // boxing: Integer
let i: int = o;        // OK（暗黙 unbox キャスト） == (o as int)
  • 成功条件：
    • E がプリミティブ P の値である。
    • または E が対応する box object（例：Integer）であり、ToXxx() で取り出せる。
  • 型変換は行わない。 数値型同士の変換や文字列パース等は行わず、該当しなければ失敗とする。

5.2.3 推奨（as / 暗黙 unbox）

  • 失敗を分岐で扱いたい場合は as P ifnot ... を推奨する。
  • 短く書きたい場合は暗黙 unbox キャストを許可するが、失敗時は例外となる。

  • const には型注釈が必須。

  • public property は Object instance の状態を外部 Object から同期的に取得するための Query とする。

7.1.2 public static property

  • public static property は型の static context に属し、特定の Object instance には属さない。
  • TypeName.Property の TypeName は型 / static 名前空間として解決し、Object Reference として評価しない。このため Object ownership / Volatile / Committed の規則は適用しない。

  • static property setter は Static CallBuffer へ enqueue しない。非同期 command が必要な場合は public static async method を使用する。
  • setter accessor 内では代入値を暗黙の value として参照できる。

7.1.3 public / private / protected instance method

  • 外部から呼び出せる public instance method は必ず async とする。
  • public async method の戻り値は必ず void とし、Task<T> / Future<T> / Promise<T> / await / continuation は導入しない。
  • Aloe の async は C# の async/await ではなく、対象 Object の CallBuffer へ method invocation を enqueue することを意味する。
  • private / protected instance method は同期実行でき、戻り値を持つことができる。
  • 実行時に targetObject == currentObject である self call は、その場で同期実行し CallBuffer へ追加しない。

7.1.4 static method

  • 通常の static method は同期実行し、戻り値を持つことができる。
  • public static async method を定義でき、その戻り値は必ず void とする。
  • public static async method は class / type ごとの Static CallBuffer を使用する。
  • C# reference VM は type ごとの FIFO queue を処理し、同じ type 内の call を逐次実行する。異なる type は VMThread pool で並列実行でき、処理中に追加された call も Quiescence まで Tick 内で処理する。

7.1.5 constructor

  • new に伴う constructor は同期実行し、Object を完全初期化した後に Object Reference を caller へ返す案を推奨する。
  • constructor は CallBuffer を経由しない。
  • constructor 完了前の this を外部 async call へ渡すことを禁止する案は未決事項とする。

Struct layout annotations: @StructLayout / @FieldOffset

Aloe は、struct のメモリレイアウトを指定するための注釈（アノテーション）を提供する。
これらは主に相互運用（バイナリ形式、外部 API 呼び出し、メモリマップ等）を目的とする。

  • @StructLayout(...) は struct 全体の配置方式を指定する。
  • @FieldOffset(n) はフィールドのオフセット（バイト）を指定する。
  • 注釈の有無にかかわらず、通常の struct の観測可能な意味（値コピー等）は変わらない。
7.2.1 @StructLayout

@StructLayout は次のいずれかの配置方式を取る。

  • Sequential：宣言順に並べる。パディングは実装が挿入してよい。
  • Explicit：各フィールドに @FieldOffset が必須となる。
  • Auto：実装が自由に配置する。外部相互運用を目的としてはならない。
@StructLayout(Sequential)
struct Header {
    field a: int;
    field b: byte;
}
7.2.2 @FieldOffset（Explicit レイアウト）

@StructLayout(Explicit) を指定した struct では、各フィールドに @FieldOffset を付けなければならない。
付いていない場合はコンパイルエラーとする。 

@StructLayout(Explicit)
struct Pixel {
    @FieldOffset(0) field r: byte;
    @FieldOffset(1) field g: byte;
    @FieldOffset(2) field b: byte;
    @FieldOffset(3) field a: byte;
}
  • オフセットが重なる場合、ビットレベルの同一領域共有として扱う（用途は相互運用に限定される）。
  • フィールドの型に対して不正なアラインメントや領域外参照となる場合はコンパイルエラーまたは実行時例外とする（検出可能な範囲は実装依存）。
7.2.3 相互運用上の注意
  • レイアウト注釈は ABI の一部となり得るため、安定性が要求される場合は explicit を推奨する。
  • 実装が異なる環境（WASM 等）ではアラインメント・パディング規則が異なり得るため、相互運用を前提とする場合はフィールドサイズとオフセットを明示する。

8.1 Dispose の基本

外部資源（ファイル、ネットワーク、ロック等）は、GC に任せず、Dispose() により明示的に解放する。
破棄（メモリ解放）は GC の責務であり、言語仕様としてオブジェクト破棄命令は持たない。

  • 資源を保持する型は Dispose() を提供してよい（標準ライブラリまたはユーザー定義）。
  • Dispose が呼ばれた後、そのオブジェクトは「破棄済み（disposed）」状態となる。
  • Dispose 後にメンバーアクセスを行った場合は ObjectDisposedException を投げる。
var r = OpenReader("file.txt");

r.ReadLine();     // throws ObjectDisposedException

using により、例外の有無にかかわらず Dispose を確実に実行できる。 using の詳細は 4.4 を参照。

8.3 Dispose の冪等性

  • Dispose() を複数回呼んだ場合の挙動は実装依存とする。
  • ただし一般に、二重解放を避けるため、同一オブジェクトの二重 Dispose は例外を投げない実装が推奨される。

  • main の生存中に main scope から直接または間接的に参照可能な Object Reference 集合を、言語意味論上の Root とする。
  • main 自身は Tick 処理、CallBuffer 実行、Tick Quiescence 判定の対象外であり、Tick を駆動する。
  • tick() は main からのみ呼び出せる Runtime intrinsic または専用 statement とし、同期 Barrier として動作する。
  • tick() が return した時点で、現在 Tick の async 処理、Volatile Commit、Reference Graph / Reference Group / Reference Count 更新、Destruction Candidate 判定は完了している。物理 GC 処理は tick() の責務に含めない。
  • GC.debug は main から読み書きできる Runtime 組み込みの public static property<bool> とし、GC の Reference Graph / Plan / Sweep / Move / FreeBlock ログを有効または無効にする。VM 命令トレースの有効状態や GC の生存判定には影響しない。

  • 1 回の program 実行中に GC debug が一度でも有効化された場合、program 終了時に [PERF] summary を出力してよい。summary は program 実行時間 elapsedMs、その実行中の累積 GC 時間 gcElapsedMs、終了時の memory metrics を含む。compile 時間は program 実行時間に含めない。
  • GC.require() は main からのみ呼び出せる Runtime intrinsic とし、通常の GC budget を守って 1 回の GC work を明示的に要求する。Plan が未完了の場合は後続の GC work へ持ち越してよい。
  • GC.finish() は main からのみ呼び出せる Runtime intrinsic とし、現在要求されている未完了 GC cycle を同期的に完了させる。active GC Plan が存在しない場合は no-op とし、新しい GC cycle を開始してはならない。生存判定は変更せず、明示的な blocking operation として通常の移動 budget を一時的に超えて処理してよい。
  • main が return するとプログラムを終了し、残存 Object Graph / Reference Group / CallBuffer は破棄可能とする。
  • main の引数・戻り値形式は既存エントリポイント規則に従う。本節は実行コンテキストと Tick 駆動の意味論を追加する。

15.1 as 演算子と ifnot（キャストと代替）

参照castプロトタイプ（2026-10-13）：E as Tはclass、object、対応済み配列の参照オペランドと対象型に対応します。class対象は宣言classと既知の派生classを許可し、配列対象は正規runtime記述子の完全一致を要求して型の不変性と階層数を維持します。オペランドは一度だけ評価し、成功時はコピーや割り当てをせず元の有効なObjectIdを返します。型不一致、Null、無効な参照はInvalidCastExceptionとなり、ifnot省略はifnot throwと同じです。E as T ifnot Fは失敗時だけFを評価し、代替参照の有効性と対象型を再検査します。Fは型文脈付き空配列や入れ子castに対応します。Fは式全体を消費するため、その結果を比較・算術式で使う場合は代替付きcastを括弧で囲みます。優先順位は単項演算より低く乗算より高く、連続cast、括弧付きclass結果のgetter読み取り、配列添字に対応します。async呼び出しは既存のローカル／with対象を使用します。getter Query内のcast検査は読み取り専用で、後続読み取りは既存のCommitted／現在状態の規則に従います。primitive同型castは以下に記載します。struct／enumへのcast、数値変換、nullable cast、直接WASMは未対応です。boxing／非消費取り出しは2.4節に記載します。class記述子は既存のコンパイラー生成の型名許可リストを使用し、VMは継承関係や任意のバイトコード記述子の真正性を独立に検証しません。参照castの設計判断（英語）を参照してください。以下の例はコンパイラーテストで実行します。
primitive同型castプロトタイプ（2026-10-13）：asの対象int、byte、char、float、decimal、string、bool／booleanに対応します。同じruntime値種別だけが成功し元の値を返します。intは符号付きint32、floatは有限値である必要があります。異なる値種別、Null、不適合なヒープ参照はInvalidCastExceptionです。asは数値変換や解析を行いません。型が一致するboxの取り出しは2.4節に記載します。例えば1 as floatや1 as byteは変換せず失敗します。同型castはfloatの負のゼロ、decimalの精度、String内容を保持します。ifnotは失敗時だけ評価し、代替式は対象型と完全一致、または期待型の文脈で暗黙に取り出せる型一致boxである必要があります。代替式に限り既存の範囲内byteリテラル文脈を許可します。オペランドは一度だけ評価し、ifnot省略はifnot throwと同じです。既存castの優先順位・連続cast・式全体を消費する代替式規則に従います。enum／struct／pipeオペランドとenum／struct対象は未対応で、ソース検査でenum型の消失を防ぎます。型一致boxからprimitiveへ取り出せるようになり、primitiveはas objectでboxingできます。名前付きbox APIは2.4節に記載します。直接WASMはcast構文を拒否します。primitive castの設計判断（英語）を参照してください。以下の例はコンパイラーテストで実行します。
function fallback(): int { print(99); return 42; }

    var same = original as int ifnot fallback();
    var replacement = 1.5 as int ifnot fallback();
    if (same == 42 and replacement == 42) { return 42; }
    return 0;
}

Aloe には括弧キャスト構文がなく、型変換は as 演算子で行う。
as は失敗時に InvalidCastException を投げる。ifnot により代替値、または throw を指定できる。 

let o: object = 123;                   // boxing: Integer




let i1: int = o as int;                // OK（unboxing）。失敗時は InvalidCastException
let i2: int = o as int ifnot -1;       // 失敗時は -1 を使う
let i3: int = o as int ifnot throw;    // 失敗時は InvalidCastException（省略時と同じ）
  • E as T の右辺 T が参照型の場合、実行時の型チェックを行う。
  • E as P の右辺 P がプリミティブ型の場合：
    • E がプリミティブ P なら成功。
    • E が対応する box object（例：Integer）なら ToXxx() により成功。
    • それ以外は失敗（InvalidCastException）。
  • ifnot を省略した場合は ifnot throw と同義とする。
  • 型変換は行わない。 数値型同士の変換、文字列パース等は行わない（パースは Parse / TryParse を用いる）。
  • ifnot 節は、キャストが失敗した場合にのみ評価する。

15.2 演算子一覧（算術 / 比較 / 論理 / ビット）

Aloe の主要な演算子は次の通りである。型付けにより不正な組み合わせはコンパイルエラーとなる。

  • 算術：+, -, *, /, %。% は int、float、decimal に対応する。int/float 混在は float に、decimal/int 混在は decimal に昇格する。
  • 単項：+x, -x, not x
  • 比較：==, !=, <, <=, >, >=
  • 論理：and, or（短絡評価）
  • ビット（int / bitfield enum）：&, |, ^, <<, >>
  • 代入：=

15.3 演算子優先順位（概要）

優先順位は一般的な言語と同様に「単項 > 乗除 > 加減 > シフト > 比較 > 等価 > ビット > 論理 > 代入」の順とする。
厳密な規則は実装が定義してよいが、曖昧さが生じる場合は括弧により明示すること。

現行の直接WASMスカラープロトタイプ（2026-10-19）：同期free functionは、型付きInt／Float／Bool／Byte／Char／enumの引数、local、戻り値に対応します。Intはi64、FloatはIEEE 754 binary32（f32）、Bool／Byte／Charはi32へ対応付け、CharはUTF-16コード単位1個をゼロ拡張します。Floatを1つ以上含む数値演算はFloat／Int／Byteオペランドに対応します。算術演算はVMと同じbinary32へ昇格し、混在比較はf64へ拡張してint32対FloatのVM順序を保ちます。Float剰余はbinary32の精度を保つ段階的な2倍化と減算で実行し、被除数の符号を維持します。非有限被除数、NaNの除数、ゼロ除数はtrapになります。無限大の除数ではVMと同様に有限な被除数を返します。その他、非有限結果、非ゼロオペランドによる乗除算結果のゼロへのunderflow、ゼロ除算、範囲外数値オペランド、非有限Float引数も実行時guardでtrapになります。decimal演算、数値変換、Syscall、配列、object操作は未対応です。ソースとAloeBCの型検査は、物理WASM型が同じscalar種別も区別します。
現行コンパイラのintビット演算（2026-10-11）：int同士の &、|、^、intの単項 ~、intとintシフト数による <<、>> に対応し、結果はintです。オペランドは実行時に符号付きint32範囲を検査し、シフト数は0..31に限定します。左シフトは上位ビットを捨て、右シフトは符号を拡張します。範囲外はVMでVmException、直接WASMでtrapとなります。byte・bool・char・float・decimal・通常enumやint/bitfield enumの混在はコンパイルエラーです。bitfield enum同士の既存演算は型を保持します。比較はビット演算より優先されるため、ビット判定は (value & mask) == mask と書きます。

17. Modules / namespace / import

Aloe のプログラムは複数ファイルから構成できる。
名前空間は namespace により宣言し、外部の宣言は import により導入する。

17.1 namespace（名前空間）

namespace MyApp.Core;




function Foo(): int {
    return 1;
}




class Bar {
}
  • ファイルは 0 個または 1 個の namespace 宣言を持つ。
  • namespace を省略した場合、そのファイルはグローバル名前空間に属する。
  • 同一 namespace に属するトップレベル宣言は互いに参照できる（4.3 の規則に従う）。

17.2 import（導入）

import MyApp.Core;
import MyApp.Utils;
  • import は他 namespace の公開宣言（型・関数・定数等）を参照可能にする。
  • 同名が衝突する場合、曖昧となりコンパイルエラーとする（4.3 の規則に従う）。
  • import のスコープはファイル単位である（そのファイル内の全ての宣言に適用される）。

17.3 アクセス修飾と公開範囲

  • トップレベル宣言はデフォルトで public として扱ってよい（実装依存）。
  • class の変数 member は public にできない。外部公開には public property を使用する。
  • instance の public property は getter による同期 Query であり、setter は存在しない。
  • public static property は static context に属し、getter と setter を定義できる。setter は同期実行する。
  • TypeName.StaticProperty の TypeName は Object ではなく型 / static 名前空間として解決する。
  • 外部から呼び出せる public instance method は public async method ... : void とする。
  • private / protected instance method は同期実行でき、戻り値を持てる。
  • 通常 static method は同期実行でき、public static async method は void の fire-and-forget command とする。
  • 名前解決は 4.3 に従い、曖昧な場合はコンパイルエラーとする。

18. Pipes & Filters（パイプとフィルタ）

Aloe は pipe<T> と filter(...) を用いて、 サーバ / CLI / Web アプリなどのストリーミング処理を構成する。

18.1 pipe<T> の基本

pipe<T> は、型 T の要素列を運ぶストリーム（参照型）である。
生成、接続、実行モデルの詳細は実装依存だが、観測可能な意味として「順序付きの要素列」であることを保証する。

  • pipe は要素を 0 個以上運ぶ。
  • 要素の順序は保存される（投入順に観測される）。
  • pipe は完了（終了）を持ち得る。完了後は追加の要素は到達しない。
  • エラーは Result により表現する（18.2参照）。

18.1.1 filter の概要

filter は pipe を入力として受け取り、処理結果の pipe を返す処理単位である。
filter はパイプラインとして連結され、データフローを形成する。 

filter Upper(input: pipe<string>): pipe<Result<string>> {
    // 概念例（詳細な構文は実装依存）
    // input の各要素を大文字化して出力する
}

18.2 Result<T> と ROP の原則

  • Result に丸めるのは原則としてパイプ（filter / producer / consumer）の中である。
  • filter / producer / consumer の bound は Result を返すのが必須であり、違反はコンパイルエラー。
  • 通常の関数・メソッドは戻り値自由（Result 強制なし）。失敗時は例外を投げてよい（その関数仕様による）。
  • 標準ライブラリは例外を投げない導線として TryParse 等を提供してよい（2.4.2参照）。

18.2.1 Result<T> と Error（失敗情報の規格）

Result<T> は、成功（Ok）または失敗（Err）のいずれかを表す結果型である。
失敗（Err）の内容は Error によって表現される。

18.2.1.1 Result<T> の意味（直和型）
  • Result<T> は Ok(value: T) または Err(error: Error) のどちらか一方の状態のみを取る。
  • Ok 状態のときは value を持ち、Err 状態のときは error を持つ。
  • 誤った状態での取り出し（例：Ok から error を取り出す等）は InvalidOperationException とする。
  • Result<T> の内部表現（フィールド構成、最適化、割当方式）は実装依存とする。ただし上記の意味は観測可能な仕様として固定する。
18.2.1.2 Error（失敗の内容）

Error は失敗の内容を表す参照型（class）であり、少なくとも次の情報を持つ。

  • code: string ... エラーコード。コード体系はドメインごとに定義される（統一 enum は作らない）。
  • message: string ... エラーメッセージ。エラー時には必須（省略不可）。
  • cause: Exception ... 原因例外。通常の失敗では未設定でよい。
18.2.1.3 cause 必須規則（例外を捕捉して Err を返す場合）
  • 例外を catch して Result の Err に変換する場合、cause を必ず設定しなければならない。
  • この規則により、例外由来の失敗が原因情報を失わないことを保証する。
try {
    // ...
}
catch (e) {
    // 例外を Err に変換する場合は cause 必須
    return Result.ErrFrom("net.http.unhandled", "Unhandled exception in http filter", e);
}
18.2.1.4 エラーコードのドメイン定義
  • エラーコードは string とし、ドメイン（namespace / module / library）ごとに定数として定義してよい。
  • 例："std.parse.format", "net.http.timeout" など。
  • Result はエラーコードの統一体系を持たず、コードの意味は定義元ドメインの仕様に従う。

18.7 コレクションに対するテンプレート map

テンプレ map の禁止事項は基本コンパイルエラーとする（静的に検出できる限り）。

19. Object / Tick / CallBuffer Runtime Model

Aloe の class Object は自身の Mutable State を所有し、外部 Object からの状態変更要求は public async method + CallBuffer を通して受け取る。 Tick 中の内部更新は Volatile State として保持し、Tick 終了時に Committed State へ確定する。

19.1 Object ownership と状態可視性

  • Object 自身だけが自身の member variable を変更できる。
  • 外部 Object は public property で状態を取得し、public async method で変更を要求する。
  • 外部 Object から class member variable を直接 Read / Write できない。
  • 外部から public property を参照した場合は Committed State が見える。
  • Object 自身が member variable を参照した場合は現在 Tick の最新 Volatile State が見え、未作成なら Committed State を読む。

19.2 Volatile State と Tick Commit

  • Object の member variable 変更は Tick 中に Committed State へ直接反映せず、Volatile State を更新する。
  • 意味論上は Object 全体に Volatile State が存在するが、実装は Dirty Member + Volatile Value のみを保持する Lazy Copy 方式でよい。
  • Tick 終了時に Volatile → Committed として確定し、Commit 後に Volatile State を破棄または reset する。
  • 従来の Field 変更用 TaskChangeBuffer / Change Record（SET / ADD / SUB 等）方式は廃止する。

19.3 Instance / Static CallBuffer

  • 各 Object は Instance CallBuffer を持ち、外部 Object からの public async method call は即時実行せず enqueue する。
  • CallBuffer への追加は排他制御し、記録順に実行する。
  • C# reference VM は同じ target Object 宛ての call を逐次実行し、Heap 操作を同期する。異なる Object は並列実行でき、順序は決定的でない。共有 Object 参照を介したアクセスには prototype が強制しない所有権規約が必要である。
  • public static async method は class / type ごとの Static CallBuffer を使用し、drain 中に追加された call を含め同一 Tick 終了までに実行する。

19.4 self call / 同期呼び出し

  • 実行時に targetObject == currentObject なら self call とし、その場で同期実行する。
  • private / protected instance method、通常 function、通常 static method は同期実行でき、戻り値を持てる。
  • Host 状態を同期的に問い合わせる static Query（例: Keyboard.isDown）を提供できるが、Host 側の Thread Safety は未決事項とする。

19.5 async CallGraph

  • public async instance method と public static async method を CallGraph 解析対象とする。
  • async method から別 async method を呼ぶ場合は edge を追加する。
  • 自己循環、2要素循環、3要素以上の循環をすべてコンパイルエラーとする。
  • interface / virtual / override 等の動的 dispatch では、静的に到達可能なすべての call 先候補を含める。
  • 循環検出には SCC 等を使用でき、必要に応じて最終 link 時にも検証する。

19.6 Tick Quiescence

Tick 開始時に存在した Call だけでなく、Tick 中に新たに enqueue された async Call も同一 Tick 内で処理する。

Running async method count == 0
AND
全 Instance CallBuffer == empty
AND
全 Static CallBuffer == empty
AND
Scheduler pending work == 0
  • 上記をすべて満たした状態を Tick Quiescence とする。
  • 通常の CallBuffer entry は次 Tick へ持ち越さない。
  • Tick 中に新規 Call が追加された場合、Quiescence には到達していない。

19.7.1 明示 GC 制御

  • GC.debug は Runtime が提供する読み書き可能な public static property<bool> とする。GC.debug = true; で GC 診断ログを有効化し、false で無効化する。var enabled = GC.debug; のように現在値も取得でき、VM 命令トレースとは独立する。
  • GC 診断ログは phase 情報に加えて、GC work ごとの elapsedMs と memory metrics（heapUsedBytes / heapReservedBytes、実装可能なら managedBytes）を含めてよい。GC debug が program 中に一度でも有効化された実行では、program 終了時に [PERF] Program end summary として program 実行時間と累積 GC 時間を出力してよい。
  • REPL は GC 診断出力を現在のセッション出力へ接続してよく、GC.debug = true; の後に GC.require() / GC.finish() を実行すると GC phase ログを対話的に確認できる。
  • GC.require() は Runtime Temporary Reference を更新した安全な状態で、通常 budget 内の GC Plan / Sweep / Move / FreeBlock を 1 回進める。
  • GC.finish() は現在要求された未完了 GC cycle が完了するまで同期的に GC を進める。active GC Plan が無い場合は何もせず return し、新規 Plan を作成しない。回収可能性そのものは GC.require() と同じ規則で判定する。
  • VM は安全な実行点で自動 GC を要求してよく、通常プログラムが明示 API を呼ぶことをメモリ回収の必須条件とはしない。
  • tick() は参照状態の確定までを担当し、GC の Plan / Sweep / Move / FreeBlock は担当しない。

VM Tick と Game Render Frame / VSYNC / Renderer / GPU は別概念とする。

19.8 Object Reference member

  • class member に Object Reference を保持できる。
  • Reference member も Committed / Volatile 規則に従う。
  • Committed Reference と Volatile Reference が異なる場合、Tick 終了までは両方の参照対象を生存させる。
  • Commit 後に Volatile Reference を新しい Committed Reference とし、旧 Committed Reference を release する。

19.9 Reference Counting と Reference Group

  • Object Reference の基本寿命管理には Reference Counting を使用する。
  • Object Reference Graph 上の SCC を Reference Group とし、一意の Group Handle を付与する。
  • 同一 Group 内の参照は Group を生存させる External Reference に数えない。
  • Group 外から Group member へ入る Reference を Group External Reference として数え、Count 0 の Group を破棄候補とする。
  • edge 追加による Group merge、edge 削除による Group split を扱い、基本的な再解析は Tick 境界に集約する。
  • Reference 型 member が変更された Object / Group を Reference Dirty として記録し、Dirty 領域を優先して再解析してよい。

19.10 Destruction Candidate と Runtime Temporary Reference

  • Reference Count 0 の Object / Reference Group は即 free せず Destruction Candidate として mark し、Tick 終了処理で安全確認後に destroy する。
  • CallBuffer 内の target Object と Object Reference argument は Call 完了まで Strong Reference とする。
  • VM Stack 上の Object Reference、実行中 method argument、CallBuffer entry、Volatile Reference は Runtime Temporary Reference として寿命計算に含める。
  • Weak Reference は初期仕様では導入しない。

19.11 async 戻り値モデル

async call は完全な fire-and-forget Command とし、Future / Promise / Task<T> / await / async return value は導入しない。 Object から値を得る場合は public property 等の同期 Query を使用する。
