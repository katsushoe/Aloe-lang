0. 概要

AloeVM は、Aloe 言語の実行用に設計された スタックベースの仮想マシン です。
ここでは以下を定義します：

  • 実行モデル（スタックマシン／フレーム構造）
  • VM レベルの値モデル（プリミティブ・構造体・クラス・enum・pipe/filter 等）
  • ヒープとメモリ管理の方針
  • パイプ / フィルタの VM 上での表現
  • AloeBC（Aloe バイトコード）バイナリ形式
  • WebAssembly（WASM）との対応ポリシー
AloeVM には 2 つの想定ランタイムがあります：
  • C# 実装（.NET 上で動作する VM）
  • WASM ネイティブ実装（aloe2wasm によって直接 WASM にコンパイルされたコード）
本仕様は主に「C# 実装 VM + AloeBC」の振る舞いを定義し、
WASM 側は「命令セットをほぼ 1:1 でマッピングする」「GC は WASM 実行系に任せる」という方針を示します。

1. 実行モデル

1.1 スタックマシンとしてのモデル

  • VM は オペランドスタック を中心としたスタックマシンである。
  • 算術命令・比較命令などはスタックトップから値を取り出し、結果を再びスタックに積む。
  • ローカル変数・引数は フレーム内ローカル領域 に保持される。

1.2 実行単位

  • 実行単位は関数 / method invocation であり、同期呼び出しは現在の VMThread 上でその場で実行する。
  • 外部 Object からの public async method invocation は対象 Object の CallBuffer に enqueue され、Scheduler が VMThread Pool 上で実行する。
  • self call は実行時の targetObject == currentObject 判定により同期実行する。
  • main() は通常 method と異なる Root / Tick Driver であり、CallBuffer では実行しない。
  • 各関数は AloeBC 内の関数テーブルに登録され、コードオフセット、ローカル変数数、引数数、例外ハンドラ参照等を保持する。

1.3 例外処理モデル

  • Aloe の try / catch / finally は VM レベルでも例外ハンドラテーブルに展開される。
  • 例外は VM 内で オブジェクト参照 として扱い、スロー時にスタックを巻き戻す。
  • WASM 実装では、ホストの例外モデルまたは多値戻り＋エラーコードパターンへマッピングする。 例外ハンドラテーブルのフォーマットは 6.6 節で定義する。

1.4 実行モード

  • VM 実行モード:
    • C# 実装 VM が AloeBC を直接読み込み、命令を逐次解釈または JIT コンパイルする。
  • WASM ネイティブモード:
    • aloe2wasm により、AloeVM 命令列をほぼ 1:1 対応で WASM 命令列へ変換し、AloeVM 自体は存在しない。
    • GC・低レベルのメモリ管理は WASM ランタイム（実行系）に委譲する。

2. VM 値モデル

2.1 VM 値のカテゴリ

VM 上で扱う値は、概念的に以下のカテゴリに分かれる。

カテゴリ 例 備考
整数（int32） int, enum, bitfield enum 32bit 符号付き整数。enum は常に int ベース。
整数（その他） byte 内部的には int32 にパックして扱ってもよい。
浮動小数点 float IEEE 754 binary32（float）。浮動小数点演算の結果は binary32 精度に丸める。
decimal decimal C# decimal と同程度の精度を持つ 128bit 近似表現（実装依存）。
bool bool 内部表現は 1byte or int32。命令セットでは int と同じ比較命令を再利用可。
char char Unicode コードポイント（実装は UTF-16 でも UTF-32 でもよい）。
オブジェクト参照 class インスタンス、string ヒープオブジェクトへのハンドル（例: 64bit ID）。
構造体 struct VM 上では「値の塊」であり、常に inline 値として扱われる（共通ヒープオブジェクトとしての boxing は行わない）。
pipe pipe<T> VM レベルで専用タグを持つ。実装は OS パイプ／ソケット等。
filter filter Foo VM レベルで専用タグ。関数＋接続情報のラッパ。
enum / bitfield enum は VM レベルでは 常に int32 として表現される。
bitfield enum の有効ビットは 0～31（最大 32 bit）に制限される。

2.2 AloeObject とヒープオブジェクト

C# 実装 VM では、ヒープ上のオブジェクトは オブジェクト ID（例: 64bit 整数） で識別される。

  • VM 上でのオブジェクト値:
    • スタックやローカルには単に objectId: long が積まれる（AloeObject）。
  • メモリマネージャ側で、オブジェクト ID → メタデータを管理する:
    • クラス／構造体の フィールドリスト（参照スロット定義）
    • フィールドごとの 値スロット（プリミティブ値 or 他オブジェクト ID）
    • trait 合成後の最終的なフィールドレイアウト
  • 構造体も同じ枠組みで扱える:
    • 構造体インスタンスは常に「親オブジェクト／配列／スタックフレームの一部」として inline で配置される。
    • VM の観点では、構造体単体を AloeObject としてヒープ管理することはなく、boxing は行わない。
    • 構造体を含むクラス／配列オブジェクト自体は、通常どおり AloeObject としてスロット上に配置される。

2.3 pipe / filter の VM タグ

  • pipe<T> と filter は、クラスインスタンスとは別の 専用 VM 値タグ を持つ。
  • ただし WASM 対応のため、内部表現は「ref 型」（例: externref / funcref / anyref 相当）にマッピングしやすい構造にする。
  • pipe は「末端バッファ＋同期オブジェクトへの参照」、filter は「バインド済みハンドラ関数＋ in/out メタ情報」などを持つ。

2.4 構造体のレイアウトとアライメント

構造体は VM 上では常に inline 値として扱われ、そのメモリレイアウトは以下のルールに従う。

  • デフォルトレイアウト（@StructLayout(Sequential) または指定なし）:
    • フィールドは ソースコードで定義された順番 に並べる。
    • 各フィールドの先頭オフセットは構造体先頭からの 8 バイト境界 に揃える。 必要に応じて前のフィールドの直後にパディングバイトを挿入する。
    • 構造体全体のサイズも 8 バイトの倍数になるよう末尾にパディングを入れてよい。
  • 明示レイアウト（@StructLayout(Explicit)）:
    • 各フィールドに @FieldOffset(n) アノテーションを付与し、構造体先頭からのオフセット（バイト単位）を明示的に指定する。
    • VM は指定されたオフセットにフィールドを配置し、重なりが発生した場合の挙動（エラー／未定義動作）は言語仕様側で定義される。
  • 自動レイアウト（@StructLayout(Auto)）:
    • VM がフィールドの順序とパディングを自由に最適化してよい。
    • この場合、バイトオフセットは安定した ABI とは見なさず、ユーザーコードが sizeof やポインタ演算で前提にしてはならない。
  • 構造体の配列:
    • 配列要素は 構造体サイズ単位で連続 に配置される。つまり N 要素の配列は N × sizeof(Struct) バイトの連続領域を占有する。
    • このレイアウトにより、3D ベクトルなどの大量の構造体を memcpy 等で一括コピーしやすい。
構造体はインタフェースを実装せず、VM から見ても仮想ディスパッチの対象にならない単純な値型として扱う。
メソッド呼び出しは「構造体を引数に取る通常の関数」として表現されるため、boxing を前提とした呼び出しパターンは存在しない。

2.4.1 @StructLayout アノテーションと VM メタデータ

本節では、言語仕様側で定義された @StructLayout / @FieldOffset アノテーションが、 AloeVM のメタデータにどのように反映されるかを定義する。
ここで述べる内容は、レイアウト情報の保持方法と ABI 的な意味付け に限定される。 GC や delete の挙動とは直接関係しない。

  • コンパイル時の取り扱い:
    • Aloe のコンパイラは、構造体定義に付与された @StructLayout と各フィールドの @FieldOffset を読み取り、型テーブルの該当エントリに以下のメタデータを埋め込む:
      • LayoutKind: Sequential / Explicit / Auto のいずれか
      • Pack: パディング単位（未指定時はデフォルト 8 バイト）。Auto の場合は「未定義」でもよい。
      • Size: 構造体全体のサイズ（バイト数）。Sequential の場合は「フィールド＋パディング」から計算、Explicit の場合は最大オフセット＋フィールドサイズから計算。
      • FieldOffsets[]: 各フィールドのバイトオフセット（LayoutKind が Explicit の場合のみ必須）。
  • VM 実行時の利用箇所（例）:
    • ネイティブ連携（FFI）:
      • C / C++ / Rust 等のネイティブコードと構造体をやり取りする際、型テーブル内の LayoutKind / Size / FieldOffsets を用いてマーシャリングコードを生成する。
      • Sequential / Explicit の場合のみ「バイトレベルで安定した ABI」として扱う。Auto の場合は ABI 前提を立ててはならない。
    • 低レベルメモリアクセス命令:
      • 将来的に「struct の特定フィールドをオフセット指定で読み書きする」ような命令（例: LD_FIELDBYOFF）を追加する場合、FieldOffsets 情報を参照して実アドレスを計算する。
    • デバッグ表示:
      • デバッガやログ出力で構造体の内部レイアウトを可視化する際に、オフセットとサイズ情報を用いる。
  • GC との関係:
    • GC（親ルートチェック・スロットアリーナ・スライディングコンパクションなど）は、基本的に「どのフィールドが参照型か」という情報だけを必要とする。
    • @StructLayout や @FieldOffset は、GC の到達可能性判定や解放タイミングには影響しない。
      （参照スロットの位置は型メタデータから決まるが、その計算にレイアウト情報を使うかどうかは実装依存。）
  • 仕様上の保証範囲:
    • Sequential / Explicit の構造体は、「同一バージョンの AloeVM / Aloe コンパイラ」間ではバイトレベルで互換なレイアウトになることを目標とする。
    • ただし、ターゲットプラットフォームやコンパイラオプションによっては、Pack や Size の扱いに差が出る可能性がある。
    • Auto レイアウトの構造体については、レイアウト安定性や ABI 互換性は一切保証しない。
  • クラスとの違い:
    • クラス（参照型）に @StructLayout を付与した場合の扱いは、言語仕様側で追加定義されるまでは「未使用／予約」とし、本 VM 仕様では具体的な意味付けを行わない。
    • 現行の AloeVM 仕様では、構造体（struct）のみがレイアウト制御の対象 として正式にサポートされる。

3. コールスタックとフレーム

3.1 フレーム構造

各関数呼び出しは「フレーム」を生成する。フレームは少なくとも以下を持つ。

  • 戻りアドレス（次に実行する命令の PC）
  • 前のフレームへのリンク
  • ローカル変数領域
  • 引数領域
  • 一時値スロット（必要なら）

3.2 呼び出し規約（概要）

  • 関数呼び出し命令（例: CALL）は、引数をスタック上に積んだ状態で実行される。
  • フレーム作成後、引数はローカル領域に移される（またはスタック上に残したままインデックス指定）。
  • 戻り値はスタックトップに 1 つだけ積まれる。
  • void 関数は戻り値を積まない。

3.3 例外フレーム

  • 例外ハンドラテーブルに基づき、スタックのどこまで巻き戻すかを決定する。
  • 巻き戻し後、catch ブロック先頭にジャンプし、例外オブジェクトをローカルまたはスタックに渡す。

4. ヒープと参照・寿命管理方針（C# 実装 VM）

4.1 スロットベースのヒープレイアウト

  • C# 実装 VM の Heap Slot は 8 バイト固定とし、Bank 内のヒープ配置における最小割り当て単位かつ配置境界とする。
  • Object の占有サイズは実データサイズを 8 バイト単位に切り上げる。たとえば実データが 20 バイトの Object は 3 Heap Slot = 24 バイトを占有し、末尾 4 バイトは padding / unused 領域となる。
  • C# 実装 VM のヒープは、8 / 16 / 32 / 64 / 128 / 256 / 512 / 1024 バイト等のサイズクラス別アリーナで管理できる。size class は Object の分類であり、Heap Slot のサイズとは別概念とする。
  • 各アリーナは、物理メモリの確保・返却単位である Bank に分割してよい。Bank は複数の Heap Slot を含む連続領域とする。
  • ヒープ Object は ObjectId / Handle で識別し、Bank 内の連続 Heap Slot を占有する。ObjectId / Handle は Object の物理 Bank / Heap Slot 位置とは独立である。
  • Bank 内の Object 開始位置は常に 8 バイト境界となる。Object table は物理位置を Bank と Heap Slot index で表現してよい。
  • Bank の具体的なサイズ、Heap Slot 数、free-list 構造は実装詳細とする。
  • 本節の Heap Slot は、VM stack / call frame 上の local slot や value slot とは別の概念である。

4.2 Object table と Runtime metadata

ObjectId から物理位置と Runtime metadata を引く Object table を持つ。

  • Arena / slot position / object size / type metadata。
  • Committed State と、現在 Tick で必要な Dirty Member / Volatile Value metadata。
  • Reference Count、Reference Group Handle、Reference Dirty、Destruction Candidate 等の寿命管理 metadata。
  • C# reference VM の現行 prototype では、class instance field 値を Object table entry の runtime metadata として保持する。field 1 個につき少なくとも 1 Heap Slot（8 byte）を物理占有量として予約し、Object Reference 型 field の書き換え時は outgoing reference edge を同時に更新する。
  • prototype compiler の new Type(args) は Object を先に確保し、同期 construct(...) を通常の VM call frame として実行してから Object Reference を caller に返す。constructor 中の this.field read/write は内部 Object field runtime operation に lower される。
  • Instance CallBuffer への参照または管理情報。
  • C# reference VM の現在の class 実装では、Object field 値と class type name metadata は Object table entry の instance state / type metadata として保持する。getter-only public property と private/protected instance method は通常の VM call frame として同期実行し、暗黙の this Object Reference を第 1 引数として受け取る。外部 instance property setter は生成しない。public async method / CallBuffer 実行は後続実装とする。

4.3 Reference Counting と Reference Group

  • Object Reference の基本寿命管理には Reference Counting を使用する。
  • Object Reference Graph 上の Strongly Connected Component を Reference Group とし、一意の Group Handle を付与する。
  • 同一 Reference Group 内の Object 間参照は Group を生存させる External Reference に数えない。
  • Group 外部から Group member へ入る Reference を Group External Reference として数える。
  • Group External Reference Count が 0 の Group は Destruction Candidate となる。
  • Group member の個別 Reference Count 情報も保持してよく、Group split / dissolve / Debug / Reference 再計算等に使用できる。

4.4 Reference member の Committed / Volatile lifetime

  • Object Reference 型 member も通常 member と同じ Committed / Volatile 規則に従う。
  • Tick 中に Reference member が変更された場合、Object 自身は Volatile Reference を参照するが、外部 Property からは Tick 終了まで Committed Reference が見える。
  • Committed Reference と Volatile Reference が異なる場合、Tick 終了までは両方の参照対象を生存させる。
  • Tick Commit 後、Volatile Reference を新しい Committed Reference とし、旧 Committed Reference を release する。

4.5 Reference Graph / Group 更新

  • Reference Graph と Reference Group の更新は基本的に Tick 境界で行う。
  • Reference 型 member が変更された Object / Group を Reference Dirty として記録できる。
  • Tick 終了時は Dirty 領域を優先的に再解析し、全 Object Graph を毎 Tick SCC 解析する必要はない。
  • 新規 edge により複数 SCC が一つになった場合は Group merge、edge 削除で SCC が分割された場合は Group split を行う。
  • Array / List / Map / struct 等を経由する間接 Object Reference を Graph edge として扱う詳細は未決事項とする。

4.6 Destruction Candidate と Runtime Temporary Reference

  • Reference Count が 0 になった Object / Reference Group は即座に free せず、まず Destruction Candidate として mark する。
  • Tick 終了処理で Runtime Temporary Reference と CallBuffer 状態を含めて安全確認した後に destroy する。
  • CallBuffer 内の target Object と Object Reference argument は Call 実行完了まで Strong Reference とする。
  • VM Stack 上の Object Reference、実行中 method argument、CallBuffer entry、Volatile Reference は Runtime Temporary Reference として寿命計算に含める。
  • Weak Reference は初期仕様では導入しない。

4.7 Bank 配置と evacuation

  • Object allocation は size class に応じた arena / Bank / slot を使用する。
  • Reference Group に属する Object は、可能な範囲で同一 Bank または少数の Bank に集約する。これは Group 単位の回収とメモリ局所性を高めるための配置方針であり、Reference Group が複数 Bank にまたがること自体は禁止しない。
  • Bank 内の全 Object が破棄可能であり、Runtime Temporary Reference や CallBuffer による Strong Reference も存在しない場合、個々の slot を解放する代わりに Bank 全体を一括して FreeBlock 対象にできる。
  • 一部の live Object のために低 occupancy Bank を保持する必要がある場合、live Object を空きのある別 Bank へ evacuation し、元 Bank を空にして一括解放してよい。
  • ObjectId / Handle は移動前後で不変とし、移動時は Object table の Bank / slot location を更新する。したがって参照元 Object や VM Stack 上の Handle を一括書き換えする必要はない。
  • 高 occupancy Bank は無理に evacuation せず、そのまま保持するか Bank 内 compaction を行ってよい。
  • 物理メモリ配置最適化は、Committed / Volatile State と Reference lifetime の観測可能な意味を変えてはならない。

4.8 GC の 3 フェーズ

C# VM の GC は、Tick 境界で次の 3 フェーズに分けて処理する。

  1. Plan phase
    • Reference Group、External Reference、Runtime Temporary Reference、Destruction Candidate、Bank occupancy を確認する。
    • sweep 対象、evacuation 元 Bank、移動先 Bank、FreeBlock 候補を決定する。
    • 少ない移動量で多くの Bank / byte を回収できる計画を優先してよい。
    • 計画中は原則として Object の物理位置を変更しない。
  2. Sweep / Move phase
    • Plan に従って dead slot を Available にし、必要な live Object を別 Bank へ移動する。
    • Object 移動ごとに Object table の物理 location を更新する。
    • Tick の移動予算に達した場合、その時点で Move を中断し、未完了の計画を次 Tick へ持ち越してよい。
  3. FreeBlock phase
    • Sweep / Move 完了後、live Object が 0 になった Bank / backing block を allocator から切り離し、物理メモリを一括して返却する。
    • まだ live Object が残る Bank は FreeBlock してはならない。

4.9 Tick ごとの GC budget

  • GC は 1 Tick 中に過大なメモリ移動を行ってはならない。Sweep / Move phase には必ず Tick ごとの有限な移動予算を設ける。
  • 少なくとも移動 Object 数または移動 byte 数のいずれかを制限し、実装は両方を制限してよい。
  • たとえば 1 Tick あたり最大 256 Object の移動という上限を設定できるが、具体的な上限値は実装およびランタイム設定に依存する。
  • Plan phase 自体も巨大 heap を毎 Tick 全走査しないよう、走査 Bank 数・処理 Object 数・処理時間等の budget を持ってよい。
  • budget 到達により evacuation が複数 Tick にまたがってもよい。途中状態でも、すでに移動した Object の ObjectId / Handle は有効でなければならない。
  • 完全に dead な Bank を一括解放できる場合、その処理は Object 移動 budget を消費しない。

4.10 WASM 実装時のメモリ管理

WASM ネイティブ実装では物理 GC / allocation を WASM 実行環境へ委譲できる。
ただし Aloe の観測可能な意味として、Object ownership、Committed / Volatile State、CallBuffer による Strong Reference、 Tick 境界の参照更新と破棄安全性を維持する。

5. パイプ / フィルタの VM 表現

5.1 pipe<T>

  • VM レベルで PIPE タグを持つ値として表現する。
  • 内部には以下のような情報を持つ想定:
    • バッファ（リングバッファ／キュー）
    • 同期プリミティブ（ロック／条件変数など）
    • 要素の型情報（ランタイム型情報への参照）
  • 複数スレッドからアクセスしても壊れないよう、実装は すべての pipe オブジェクトをスレッドセーフ にする必要がある。
    • これは AloeVM 全実装に共通の仕様上の要求であり、C# 実装に限らない。
    • ロック方式（ミューテックス、スピンロック、ロックフリーキュー等）は実装依存とする。
  • 実装例:
    • OS パイプ／ソケット
    • メモリマップドファイル上のリングバッファ

5.2 filter

  • filter は専用タグ（FILTER）を持つ値として表現される。
  • filter 値は、概念的には
    • 「bound 関数へのポインタ」
    • フィルタ定義メタ情報（in/out 型）
    をまとめた構造体。
  • ユーザ定義フィルタも同じ仕組みで表現できる。

5.3 パイプライン文の実行モデル


A | filter(F) | B;
  • VM はこの文を「接続構築命令」の列に展開する。
  • 典型的な流れ:
    1. A の出力 pipe を解決する。
    2. filter(F) のインスタンスを生成し、bound(input, output) を別タスク／スレッドとして起動。
    3. 出力 pipe を B に接続する。
  • ただし、実際に「フィルタごとにスレッドを起こすかどうか」は VM 実装に依存する。
    • 仕様としては、「各 filter / producer / consumer がどのスレッドで実行されるか」は VM 実装依存 とし、Aloe 言語仕様および AloeVM 仕様では固定しない。
    • C# 版 AloeVM のデフォルト実装では、パイプライン全体を 1 本のスレッドで実行するモデル を採用し、実装を簡潔に保つ。
    • 他の実装（例えば高スループットなサーバ向け実装）では、ワーカースレッドプールで共有実行するモデルを採用してもよい。
  • このため、Aloe プログラム側は「どの filter がどのスレッドで動くか」に依存したロジック（スレッドローカル変数に依存する挙動など）を書いてはならない。
    • スレッド数やスケジューリング戦略は、VM のチューニングや環境によって自由に変更されうる。

5.4 パイプのライフサイクルと VM 命令

pipe は VM レベルでは、概ね次の 4 フェーズを持つライフサイクルとして扱う： 生成 → 接続 → 切断 → 削除。 それぞれのフェーズは、7 章で定義する「pipe / filter / 接続カテゴリ（カテゴリ ID = 0x0A）」の命令によって操作される。

  • 生成フェーズ（Create）
    • 新しい pipe インスタンスを確保し、バッファや同期オブジェクトを初期化する。
    • 代表的な命令（例）:
      • PIPE_NEW:
        • 引数として要素型 ID、バッファサイズ、オプションフラグなどを取る。
        • 戻り値として pipe ハンドル（VM 値としての PIPE タグ付きハンドル）をスタックに積む。
  • 接続フェーズ（Connect）
    • 既存の pipe に対して、producer / consumer / filter を接続する。
    • 代表的な命令（例）:
      • PIPE_BIND_PRODUCER:
        • pipe ハンドルと producer 側エンドポイント（メソッド／タスク）を結び付ける。
      • PIPE_BIND_CONSUMER:
        • pipe ハンドルと consumer 側エンドポイントを結び付ける。
      • PIPE_CONNECT:
        • 複数の pipe と filter をまとめて「パイプライン」として接続する高レベル命令として定義してもよい。
  • 切断フェーズ（Disconnect）
    • producer / consumer / filter を pipe から切り離し、新たなデータの流入・流出を止める。
    • 代表的な命令（例）:
      • PIPE_DISCONNECT:
        • 指定したエンドポイントを pipe から切り離す。
        • 既にバッファ内に存在するデータの扱い（破棄する／最後まで読み出させる）は実装ポリシーで決める。
  • 削除フェーズ（Delete / Close）
    • pipe 自体をクローズし、関連するバッファや同期オブジェクトを解放する。
    • 代表的な命令（例）:
      • PIPE_CLOSE:
        • pipe ハンドルをクローズし、GC から見て到達不能になった時点で、ヒープ上の pipe オブジェクトが解放候補となる。
    • Aloe 言語レベルの delete や with ブロック終了時の暗黙クローズは、 これらの命令にコンパイルされる想定である。
producer / consumer として動作するコードは、通常は「通常の関数／メソッド＋スレッド（またはタスク）」の組み合わせで表現される。
必要に応じて、PRODUCER_START, PRODUCER_STOP, CONSUMER_START, CONSUMER_STOP のような 制御専用命令を 0x0A カテゴリ内に追加してもよい。

5.5 C# 版 AloeVM の協調スケジューラ

  • C# 版 AloeVM は、main とバインドされた各 filter を 1 本の VM スレッド内の別々の実行コンテキストとして実行する。各コンテキストは自身のコールフレームと評価スタックを持ち、切り替え時に保存・復元される。
  • 実行可能なコンテキストは FIFO キューで管理する。1 回の実行は一定の命令数（現在 1024 命令）までとし、その後キュー末尾へ戻す。同じコンテキストを重複してキューへ入れない。
  • 満杯の bounded pipe への書き込みは、読み取りで空きができるか pipe が close されるまで書き込み側を待機させる。空で close されていない pipe からの読み取りは、値が届くか close されるまで読み取り側を待機させる。
  • コンテキストの最外フレームからの return は、そのコンテキストだけを完了させる。他のコンテキストは停止しない。main が残した値がプログラムの戻り値となる。
  • 未完了のコンテキストが残っているのに実行可能なコンテキストがない場合、VM は未完了数と読み取り待ち・書き込み待ちの件数を含む Pipe scheduler deadlock エラーを報告する。
  • プロパティ getter と tick() が処理するインスタンス呼び出しは、1 つの SYSCALL 内で同期的に実行され、中断できない。この中で待機が必要になる pipe 操作は VM エラーとする。待機を伴わない pipe 操作は許可する。
  • 待機中のコンテキストが持つフレームローカルと評価スタックの値は GC ルートとして扱う。

6. AloeBC バイナリ形式

6.1 全体構造

AloeBC（Aloe Byte Code）は、AloeVM 向けコンパイル結果を格納するバイナリフォーマットである。

6.2 ヘッダ

オフセット サイズ フィールド 内容
0 6 byte Magic ASCII 文字列 "ALOEBC"
6 1 byte VersionMajor メジャーバージョン
7 1 byte VersionMinor マイナーバージョン
8 1 byte VersionBuild ビルド番号
9 1 byte Reserved 予約（0 固定）
10 4 byte HeaderSize ヘッダ全体のサイズ（リトルエンディアン）
14 4 byte ConstPoolOffset 定数プールの先頭オフセット
18 4 byte TypeTableOffset 型テーブルの先頭オフセット
22 4 byte FuncTableOffset 関数テーブルの先頭オフセット
26 4 byte CodeSectionOffset コードセクションの先頭オフセット

エンディアンは リトルエンディアン を前提とする。

6.2.1 C# リファレンス実装の 0.1 セクションプロファイル

現行 C# リファレンス実装の AloeBcCodec は、最終的な TypeId ベース形式へ移行する前段階として、 10 byte の固定ヘッダに続けて自己記述的な section を並べる 0.1 プロトタイププロファイルを実装する。 このプロファイルは C# VM / compiler 間の round-trip と verifier 接続を先に成立させるための実装プロファイルであり、 下記 6.4 の完全な TypeId 形式へ段階的に統合する。 
Header:
  Magic        6 byte  "ALOEBC"
  VersionMajor 1 byte  0
  VersionMinor 1 byte  1
  VersionBuild 1 byte  0
  Flags        1 byte  0

Section:
  SectionId    u8
  PayloadSize  i32 little-endian
  Payload      byte[PayloadSize]
SectionId名前C# 0.1 プロファイルの内容
0x01TYPE関数ごとの型メタデータ。型付き関数では引数型、全 local slot 型、戻り値型を保持する。旧 FunctionInfo は parameter/local count のみを保持する。
0x02CONSTANT定数列。現行 codec は int、IEEE 754 binary32 の float（4byte）、bool、decimal、UTF-8 string を格納する。decimal payload はC# decimalの内部表現に対応する符号付き32bit値4個（little-endian）である。
0x03FUNCTIONEntryPointIndex、関数名、命令配列中の EntryIp を格納する。
0x04CODE命令数と、各命令の opcode:u16 + operand0:i32 + operand1:i32 を格納する。
0x80-0xFFCustom / Extension未知の場合でも PayloadSize により読み飛ばしてよい。
  • 0x01-0x7F の未知 core section はロードエラーとする。
  • 同一 core section の重複、必須 section 欠落、payload 境界超過、無効 UTF-8、未知 opcode / value kind はロードエラーとする。
  • デシリアライズ後の Module は AloeVM 実行前に verifier を通過しなければならない。
  • 現行 C# 実装の int 定数は AloeValue の内部表現に合わせて signed 64-bit で保存する。言語仕様上の最終 int 幅と AloeBC 正規表現は TypeId 形式確定時に再固定する。

6.3 定数プール（概要）

  • 文字列リテラル、数値リテラル、型情報などを一元管理する。
  • 各エントリは「タグ + 長さ + 本体」で構成される可変長レコード。
  • タグの例:
    • 0x01: UTF-8 文字列
    • 0x02: int32
    • 0x03: float32（binary32）
    • 0x04: decimal

6.4 型テーブル

AloeBC の型情報は、プリミティブ型・複合型・関数型を含めて TypeId で一元参照する。 命令や関数シグネチャが型を必要とする場合は、可能な限り TypeId を使用する。

  • 各 Aloe 型（primitive / class / struct / enum / bitfield enum / pipe<T> / function type など）に TypeId を割り当てる。
  • pipe<T> は単なる PIPE タグではなく、要素型の TypeId を保持する複合型として表現する。したがって pipe<int> と pipe<string> は異なる型である。
  • 関数型は引数 TypeId 列と戻り値 TypeId（void の場合は戻り値なし）を保持する。
  • enum / bitfield enum は VM 上では int32 値型 として表現するが、TypeId 上は元の Aloe 型を識別できる。
  • bitfield enum の有効ビット数（0～31）はメタ情報として保持してもよい（警告発生などに利用）。
Type Table は「関数シグネチャ専用表」ではなく、AloeBC 全体の型を表す正規の型表とする。 これにより verifier は PIPE<T>、ローカル、引数、戻り値を同じ TypeId 空間で検証できる。

6.5 関数テーブル・コードセクション

  • 関数テーブル:
    • 関数シグネチャ（引数の型、戻り値の型）
    • ローカル変数の数
    • コードセクション内のオフセット・長さ
    • 例外ハンドラテーブルのエントリ数および先頭オフセット
  • コードセクション:
    • VM 命令列をバイト列として格納。
    • 命令セットの詳細は第 7 章参照。

6.6 例外ハンドラテーブル

各関数には 0 個以上の例外ハンドラエントリを持つテーブルを関連付ける。 関数テーブル内の情報を用いて、当該関数のコード先頭からの相対オフセットとエントリ数を取得できる。

フィールド名 型 内容
TryStartOffset uint32 関数コード先頭からのオフセット（バイト単位）。try ブロックの開始位置（inclusive）。
TryEndOffset uint32 try ブロックの終了位置（exclusive）。範囲は [TryStartOffset, TryEndOffset) と解釈する。
HandlerStartOffset uint32 対応するハンドラブロック（catch / finally / filter）の先頭オフセット。
HandlerEndOffset uint32 ハンドラブロックの終了オフセット（exclusive）。
HandlerKind uint8 ハンドラ種別。 例: 0 = catch, 1 = finally, 2 = filter（将来拡張用に 3 以降は予約）。
Reserved uint8[3] パディングおよび将来拡張用。現行仕様では 0 固定。
ExceptionTypeId uint32 HandlerKind == catch の場合に有効な例外型 ID（型テーブルへのインデックス）。
0 を指定した場合は「任意の例外（catch-all）」を意味する。
finally の場合は 0 固定、filter の場合の扱いは将来拡張。
  • 1 つの try 範囲に対して複数の catch を持つ場合、 TryStartOffset / TryEndOffset が同一で HandlerKind = catch のエントリを複数並べる。
  • catch の評価順序はテーブル内の並び順に従う。
  • finally ブロックは、同じ try 範囲に対して 0 または 1 個のエントリを持つことができる。

6.7 AloeBC verifier

AloeVM は関数コードを実行する前に AloeBC を検証する。検証済みコードでは、VM は各命令ごとに 型・ローカル index・関数 index・branch depth を再検証する必要はない（実装上の defensive check は許可する）。

  • 未知 opcode、範囲外の constant / local / function / TypeId を拒否する。
  • オペランドスタックの underflow と型不一致を拒否する。int32 と bool は実装表現が同じでも型として区別する。
  • BLOCK / LOOP / IF / ELSE / END のネストが正しいことを検証する。
  • BR / BR_IF の branch depth が現在の control stack 内に収まることを検証する。
  • v0.1 の structured block は結果値を持たない。block / loop / if の正常終了時および branch 時には、オペランドスタック高さが対象 control frame の開始時と一致しなければならない。
  • CALL は callee の関数型に従い、引数型を pop し、戻り値があればその型を push する。
  • pipe<T> 命令は要素型まで検証する。たとえば pipe<string> への int32 書き込みは validation error とする。
  • 非 void 関数は、到達可能なすべての終了経路で正しい戻り値を返さなければならない。

BR または RET 後の到達不能領域では、WebAssembly と同様にスタックを polymorphic として扱ってよい。 ただし opcode、index、control structure 自体の構造検証は継続する。

6.8 validation error と runtime trap

  • validation error: 型不一致、stack underflow、不正 index、不正 branch depth、壊れた control nesting など。実行開始前に拒否する。
  • runtime trap / exception: 0 除算、closed pipe への write、空 pipe に対する不正な read、host runtime failure など。bytecode 自体は構造上正しいため実行時に処理する。

7. 命令セットと WASM 対応（概要）

7.1 命令カテゴリ

命令セットはおおよそ以下のカテゴリに分かれる想定であり、各カテゴリには 1 バイトのカテゴリ ID を割り当てる。

  • スタック操作命令
    • PUSH, POP, DUP, SWAP など
  • 算術・論理命令
    • ADD, SUB, MUL, DIV, MOD
    • AND, OR, XOR, SHL, SHR
  • 比較命令
    • CMPEQ, CMPNE, CMPLT, CMPLE, CMPGT, CMPGE
  • 制御フロー命令
    • BLOCK, LOOP, IF, ELSE, END, BR, BR_IF
  • 関数呼び出し命令
    • CALL, RET
  • オブジェクト操作命令
    • NEWOBJ, GETFIELD, SETFIELD など
  • 配列・コレクション操作命令（将来）
  • pipe / filter / producer / consumer / 接続・切断命令
  • 例外処理・VM 管理・デバッグ命令
本仕様書では、命令カテゴリと ID 構成のポリシーのみを定義する。
個々の命令ごとのオペコード値やビット配置は、別資料「AloeVM 命令セットリファレンス」で詳細に定義する。

7.2 命令 ID の構成（カテゴリ + 連番）

AloeVM の各命令には、16bit（2 バイト）の命令 ID を割り当てる。
命令 ID は上位 1 バイトを カテゴリ ID、下位 1 バイトを カテゴリ内連番 として扱う。

  • 16bit 命令 ID の構成:
    • 上位 8bit: カテゴリ ID（例: スタック操作 = 0x01, 算術 = 0x02 など）
    • 下位 8bit: カテゴリ内での連番（そのカテゴリのオペコード表の並び順）
  • 数式で表すと、命令 ID は次のように求めることができる： 
    OpcodeID = (Category << 8) | IndexInCategory
  • 具体例:
    • スタック操作カテゴリ（カテゴリ ID = 0x01）の 1 番目の命令 → 0x0101
    • 同カテゴリの 2 番目の命令 → 0x0102
    • 算術カテゴリ（カテゴリ ID = 0x02）の 3 番目の命令 → 0x0203
カテゴリ ID（上位 1 バイト） カテゴリ名（例） 備考
0x01 スタック操作命令 PUSH, POP, DUP, SWAP など
0x02 算術命令 ADD, SUB, MUL, DIV, MOD など
0x03 論理・ビット演算命令 AND, OR, XOR, SHL, SHR など
0x04 比較命令 CMPEQ, CMPNE, CMPLT, CMPLE, CMPGT, CMPGE
0x05 制御フロー命令 BLOCK, LOOP, IF, ELSE, END, BR, BR_IF
0x06 呼び出し・戻り命令 CALL, RET など
0x07 メモリアクセス命令 ローカル／引数／グローバル／フィールドの load/store など
0x08 オブジェクト / 配列命令 NEWOBJ, NEWARR, GETFIELD, SETFIELD など
0x09 例外・エラー命令 THROW, RETHROW, LEAVE など
0x0A pipe / filter / 接続命令 pipe 生成・接続・切断・producer/consumer 起動など
0x0B VM 管理・デバッグ命令 NOP, HALT, BREAKPOINT など
0xF0〜0xFF 実装依存・実験用命令 特定実装でのみ使用される拡張命令の予約領域

7.3 命令セット詳細の参照先

個々のオペコード ID・オペランド形式・バイナリ表現の詳細な一覧は、 本仕様書ではなく別資料「AloeVM 命令セットリファレンス」で定義する。
実装者は、本章のポリシーとカテゴリ設計を前提としたうえで、命令セットの具体的な定義については 命令セットリファレンスを参照すること。

7.4 Structured control flow

AloeBC v0.1 の制御フローは、任意 byte offset への JMP ではなく、WebAssembly と同系統の structured control flow を採用する。

  • BLOCK / LOOP / IF は control label を作成し、END で閉じる。
  • ELSE は直前の未完了 IF に対応する。
  • BR depth / BR_IF depth は byte offset ではなく、現在位置から何段外側の control label を対象にするかを unsigned depth で指定する。最内側を depth 0 とする。
  • BR 0 の対象が LOOP の場合は loop 先頭へ戻り、BLOCK / IF の場合は対応する END の直後へ移る。
  • 任意アドレス分岐命令 JMP / JMP_IF_* は v0.1 core opcode として定義しない。

7.5 WASM への 1:1 マッピング方針

  • BLOCK, LOOP, IF, ELSE, END, BR, BR_IF は WASM の対応命令へ直接的にマッピングする。
  • 基本算術・比較命令は、可能な限り WASM の i32.add, i32.lt_s などへ 1:1 でマッピングする。
  • 例外処理は、WASM の exception handling 拡張またはエラーコード + structured block の組み合わせで表現する。
  • pipe / filter は、WASM の ref 型＋ runtime / host function を用いて lowering する。

7.6 aloe2wasm の役割

  • Aloe ソース → AloeBC → AloeVM 実行 という経路とは別に、
    • Aloe ソース → 中間 IR → WASM という ネイティブ WASM ビルド 経路を用意する。
  • このとき、AloeVM 命令セットと WASM 命令セットが近いほど、コンパイラ実装が単純になる。
  • 理想的には「AloeVM 命令列をそのまま WASM にシリアライズするだけ」で動作するレベルを目指す。

8. Object / Tick / CallBuffer 実行モデル

AloeVM は複数 VMThread 上で Object の async command を実行するが、Mutable State の所有単位は Task ではなく Object とする。 外部 Object は public property によって Committed State を取得し、public async method によって状態変更を要求する。

8.1 Object ownership

  • class Object は自身の member state を所有し、その Object 自身だけが変更する。
  • 外部 Object から class member variable を直接 Read / Write しない。
  • Tick 中の内部変更は Volatile State に反映し、Committed State は Tick 終了まで変更しない。

8.2 public property と状態可視性

  • 外部 Object から instance public property getter を実行した場合、対象 Object の Committed State を読む。
  • Object 自身は最新の Volatile State を読み、Volatile 値が無い member は Committed 値を読む。
  • instance public property setter は存在しない。

8.2.1 public static property

  • public static property は Object instance ではなく type の static context に属する。
  • TypeName.Property の TypeName は Object Reference ではなく型 / static 名前空間として解決するため、Object ownership / Volatile / Committed の状態可視性規則は適用しない。
  • getter と setter を定義でき、setter は TypeName.Property = value; により同期実行する。Static CallBuffer には enqueue しない。
  • 非同期の static command が必要な場合は public static async method を使用する。

8.3 Volatile State

  • Object member の Write は Tick 中に Volatile State を直接更新する。
  • 実装は全 Object State を copy せず、Dirty Member + Volatile Value の Lazy Copy を使用してよい。
  • C# reference VM の現行 prototype は Object table entry ごとに Committed field と dirty な Volatile field overlay を保持する。async method 内の self/internal field read は dirty な Volatile 値を優先し、外部 public property query は同 Tick 中でも Committed 値を読む。
  • Object Reference 型 field を Tick 中に変更した場合、旧 Committed Reference と新 Volatile Reference の両方を Tick Commit まで strong edge として保持する。これにより同 Tick 内の Query 可視性と GC liveness を一致させる。
  • tick() は Instance CallBuffer が Quiescence に到達した後に dirty Volatile fields を Committed State へ昇格し、その後 Reference Graph を更新して main へ戻る。
  • Tick Commit 後、Volatile State を破棄または reset する。
  • Field 変更履歴を記録する TaskChangeBuffer / Change Record 方式は廃止する。

8.4 Instance CallBuffer

  • 各 Object は CallBuffer を持つ。
  • C# reference VM は public async instance method を対象 Object、function index、引数列を持つ pending entry として保持する。同一 Object 宛ての call は FIFO で逐次実行し、異なる Object 宛ての call は別 VMThread pool worker で並列実行できる。処理中に enqueue された call も含め、queue と worker が Quiescence になるまで tick() は待機する。
  • pending entry の target Object と Object Reference 引数は、entry が未処理の間 Runtime Temporary Root として GC から保護する。これは将来の per-Object CallBuffer strong-reference metadata 実装と同じ生存意味を持つ。
  • 外部 Object からの public async method call は即時実行せず CallBuffer に enqueue する。
  • CallBuffer 追加は排他制御し、Buffer entry は記録順に実行する。
  • CallBuffer entry は target Object と Object Reference argument を Call 完了まで Strong Reference として保持する。

8.5 CallBuffer 順序と決定論

  • C# reference VM は CallBuffer と Heap 操作を同期し、同一 target Object 宛ての call を重複実行しない。
  • 別 Object 間の処理順は scheduling によって変わる。同じ参照先 Object を複数 worker から操作するコードには所有権規約が必要だが、prototype は参照を辿った Object 所有権を強制しない。
  • 完全決定論が必要な場合の Sender Object ID / Sender Sequence / Logical Call Order 等は将来仕様とする。

8.6 self call と同期処理

  • targetObject == currentObject の self call は CallBuffer に enqueue せず同期実行する。
  • private / protected instance method は同期実行でき、戻り値を持てる。
  • 通常 function と通常 static method は同期実行し、戻り値を持てる。

8.7 Static CallBuffer

  • public static async method は class / type ごとの Static CallBuffer を使用する。
  • C# reference VM は type ごとの Static CallBuffer を FIFO で処理し、同一 type の call は同時実行しない。異なる type の call は並列実行できる。処理中に enqueue された call も同じ Tick 内で処理する。

8.8 async CallGraph

  • public async instance method と public static async method を CallGraph 解析対象とする。
  • async → async call を edge とし、自己循環を含むすべての cycle を Compile Error とする。
  • 動的 dispatch は静的に到達可能なすべての call 先候補を Graph に含め、必要なら最終 link 時にも検証する。
  • SCC 等のアルゴリズムで cycle を検出できる。

8.9 Tick 中に生成された Call

  • Tick 開始時に存在した Call だけでなく、async method 実行中に enqueue された新規 Call も同じ Tick 中に実行する。
  • 通常の CallBuffer entry は次 Tick へ持ち越さない。

8.10 Tick Quiescence

Running async method count == 0
AND
all Instance CallBuffers == empty
AND
all Static CallBuffers == empty
AND
Scheduler pending work == 0

上記をすべて満たした状態を Tick Quiescence とする。新しい Call が追加された場合は Quiescence ではない。

8.11 main() と tick()

  • main() はプログラム開始時に一度実行される Root Scope / Tick Driver であり、CallBuffer と Quiescence の対象外とする。
  • main scope から直接または間接的に参照可能な Object Reference 集合を言語意味論上の Root とする。
  • tick() は main からのみ呼び出せる Runtime intrinsic または専用 statement とする。
  • tick() は同期 Barrier であり、return 時には async 処理、Volatile Commit、Reference Graph / Reference Group / Reference Count 更新、Destruction Candidate 判定が完了している。GC Plan / Sweep / Move / FreeBlock は tick() から分離する。
  • main が return するとプログラムを終了し、残存 Object Graph / Reference Group / CallBuffer は破棄可能とする。

8.12.1 明示 GC Runtime intrinsic

  • GC.debug は Runtime が提供する読み書き可能な public static property<bool> とし、main から参照 / 変更できる。true の間は Reference Graph / Plan / Sweep / Move / FreeBlock 等の GC 診断ログを出力し、false で停止する。VM instruction trace の有効状態とは独立し、GC の生存判定や budget を変更しない。
  • GC work の完了ログには計測可能な範囲で elapsedMs、heapUsedBytes、heapReservedBytes を含める。C# reference VM は参考値として System.GC.GetTotalMemory(false) による managedBytes も出力する。
  • C# reference VM の GC debug は [GC] Timing: として referenceGraphMs / planMs / sweepMs / moveMs / freeBlockMs / totalMs を個別に出力し、cold-start や特定 phase のコストを判別できるようにする。
  • heapUsedBytes は現在 live な Aloe Object が占有する固定長 Heap Slot の合計 byte 数、heapReservedBytes は現在確保されている全 Bank の容量合計とする。
  • program 実行中に GC debug が一度でも true になった場合、C# reference VM は program 終了時に [PERF] Program end を出力する。elapsedMs は VM entry point 実行開始から終了までとし compile 時間を含めない。gcElapsedMs は同一 program run 中に実行した GC work の累積時間とする。
  • [PERF] summary は Host managed heap の切り分け用に managedStartBytes / managedBytes / managedDeltaBytes、同一 program run 中の Host managed allocation 増分 allocatedDeltaBytes、および .NET GC collection 回数差分 hostGcGen0 / hostGcGen1 / hostGcGen2 を出力してよい。これらは Aloe Heap の生存判定とは独立した Host 診断値であり、診断のために Host GC を強制実行してはならない。
  • REPL 実装は GC 診断ログの出力先を REPL セッション出力へ接続してよい。
  • GC.require() は main からのみ呼び出せる Runtime intrinsic とする。VM は現在の stack / frame local / CallBuffer 等から Runtime Temporary Reference を更新し、通常の GC budget 内で 1 回の Plan / Sweep / Move / FreeBlock work を進める。
  • GC.require() で Plan が完了しない場合、active Plan を後続の GC work に持ち越してよい。
  • GC.finish() は main からのみ呼び出せる blocking Runtime intrinsic とする。active GC Plan が存在する場合、その現在要求された GC cycle が PlanCompleted になるまで同期的に処理する。active GC Plan が存在しない場合は no-op とし、新しい Plan / GC cycle を開始してはならない。
  • GC.finish() は Object / Reference Group の生存判定規則を変更しない。完了を保証するため、実装はこの明示操作中だけ通常の移動 Object 数 / byte 数 budget を一時的に緩和してよい。
  • VM は memory pressure 等に応じ、安全な実行点で GC.require() 相当の自動 GC を開始してよい。明示 API は通常の自動回収を無効化しない。

8.13 VMThread Pool と Scheduling

  • C# reference VM は worker ごとに operand stack と call stack を分離する。AloeVm.MaxVmThreads が worker 数の上限を定め、既定値は processor 数である。
  • 同一 Object の Instance CallBuffer と同一 type の Static CallBuffer は同時に一件だけ実行し、異なる Object / type の call は並列実行できる。
  • Heap 操作は同期する。Heap 構造と個々の field 操作を保護するが、複数 Object にまたがる transaction や、引数から辿れる Object の所有権までは保証しない。
  • Host syscall callback は VM ごとに直列化する。Pipe 状態も同期し、worker 内の blocking pipe 操作は suspend せず VM error にする。
  • tick() の worker queue 処理中は GC を実行できない。新規 enqueue を含む worker が終了してから Volatile State を commit する。

8.14 Game Frame との分離

  • VM Tick と Game Render Frame は同一概念ではない。
  • VM は Renderer / VSYNC / Frame Clear / GPU を認識しない。
  • Host Runtime は Input 処理 → Aloe commands → tick() → Physics → Render 等の順で VM Tick を利用できる。

8.15 Host synchronous Query

  • Keyboard.isDown / isPressed 等、Host 状態を同期的に問い合わせる static method を提供できる。
  • C# reference VM は登録済み Host syscall callback を直列化する。この callback 経路外で Host state を共有する場合の安全性は Host 側の責任である。

8.16 async failure と Tick atomicity

C# reference VM では worker の未処理例外を Tick Failure とする。実行中 worker を合流し、未開始の call を破棄し、 Volatile State を commit せず、最初の worker 例外を tick() から main へ再 throw する。 VM は次のプログラム実行まで fault 状態となる。失敗前に完了した Host 副作用は rollback できない。
