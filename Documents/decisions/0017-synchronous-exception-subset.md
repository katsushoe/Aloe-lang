# Synchronous Exception Subset

Status: Implemented; ordered catch clauses added 2026-10-19.

## Context

The language specification describes typed exception handling, rethrow and `finally`, while the VM implementation has no exception values. Async CallBuffer propagation and Tick rollback are unresolved. A bounded implementation can support catch ordering without introducing a new AloeBC section.

## Decision

Implement synchronous `try` with one or more ordered catch clauses and bare `throw;` rethrow. A handler catches .NET exceptions raised while executing Aloe bytecode in the same synchronous call stack, including exceptions from synchronous callees. Exception dispatch unwinds callee frames to the nearest active handler, restores the value-stack snapshot and structured-control depth captured at `try`, and enters the first assignable catch body. A catch-all clause may appear only last. A normal exit removes the handler. A branch outside the try instruction range expires it. `throw;` propagates the same exception while retaining its active catch context until dispatch selects a handler. Each try records its enclosing caught-exception depth; dispatch discards only contexts exited on the way to the selected handler, then pushes the newly caught exception. This permits an inner try to handle rethrow and resume inside the enclosing catch without losing that catch context. An uncaught exception escapes the VM unchanged.

Catch handlers do not bind an exception value. Type-only clauses such as `catch (ZeroDivisionException)` match the existing supported .NET exception type and its derived classes. Clauses are tested in source order; the first assignable clause is selected. Supported names are `Exception`, `SystemException`, `ZeroDivisionException`, `InvalidReferenceException`, `InvalidCastException`, `OverflowException`, `ArgumentException`, `IndexOutOfRangeException`, and `VmException`. A nonmatching exception continues searching outer active handlers and escapes unchanged if none match. The list is explicit; arbitrary CLR type loading is not supported. Exception construction, `throw expression`, `finally`, exception handling inside async functions and direct WASM remain unsupported. The separate `as T ifnot throw` cast fallback is unaffected. Async CallBuffer propagation and Tick failure/rollback remain outside this decision.

The current prototype uses instruction values `0x00A4` (`TRY_BEGIN`, absolute catch-table IP), `0x00A5` (`TRY_END`), `0x00A6` (`CATCH_END`), `0x00A7` (`TRY_CATCH`, absolute catch-body IP plus exception-name constant index + 1; zero means catch-all) and `0x00A2` (`RETHROW`). The ordered descriptors are stored in the code stream; no AloeBC section or Module layout is added. Handler and currently caught exception state stay on `CallFrame`. Older runtimes that do not implement these opcode values reject bytecode containing the new instructions.

## Alternatives

- Add a complete exception-region table and typed exception value model: deferred because object representation and async rollback semantics are not settled.
- Resolve arbitrary CLR names dynamically: rejected to keep the language surface explicit.
- Implement `finally` by duplicating bytecode at each exit: deferred because return, break, continue, rethrow and nested regions require shared exit semantics.

## Impact and conditions

The compiler rejects unknown exception names, catch variables, a catch clause after catch-all, async function bodies containing exception syntax, `finally` and direct WASM exception syntax. The bytecode verifier validates catch-table descriptors, targets and exception-name constants within the same function/module. Tests cover same-frame faults, synchronous callee unwinding, value-stack restoration, rethrow, exact/base type matching, ordered multi-catch selection, mismatch propagation to an outer handler, exceptions thrown from a catch body, normal flow, exiting a try via `break`, unsupported syntax, AloeBC round-trip and unhandled propagation. Exception values, `finally` and async propagation remain future work.

## Interface flow refinement (2026-10-22)

For constant-int local declarations and assignments, the compiler distinguishes guaranteed zero division from checked int32 overflow when deciding which typed catches can affect continuing interface facts. Statically selected `if`/`else if`/`else` branches are followed recursively; a selected branch that completes normally continues with the following statement, and a statically false `while` is skipped. A statically true loop with a guaranteed arithmetic exception retains that exception type. A statically true loop whose supported body completes normally does not make later statements reachable. The same exception distinction applies to constant-int comparisons in conditions, respecting left-to-right evaluation, boolean operator precedence and short circuiting. A right operand's failure is exact only after the left operand is proven safe, or when the left operand itself has an exact guaranteed failure that prevents right evaluation. For a condition proven nonthrowing from primitive bool local/parameter reads, constant comparisons and short-circuit boolean operators, both possible branches may join when they have the same supported arithmetic outcome. Equal normal outcomes continue to following statements; equal exact failures retain their exception type. The same nonthrowing bool analysis recognizes masked-false while conditions and always-true bool combinations, while possible zero-iteration and unknown-call conditions remain conservative. Conditions containing potentially executed unknown calls, unsupported return expressions, statements and control transfers retain conservative catch reachability. Unreachable handlers are still parsed and type checked. These refinements do not change runtime dispatch or the exception model.

2026-10-22 refinement: nonthrowing bool locals/parameters and their boolean expressions also support bool equality and inequality when both operands are within this nonthrowing subset. Outcome combinations are conservative; relationships between repeated reads are not inferred. Comparisons containing calls retain unknown exceptional edges. The existing equal-arithmetic-outcome branch join and masked while-condition logic consume these outcomes without changing VM behavior.

2026-10-22 finite arithmetic exception outcomes: supported nonthrowing bool branches retain the union of possible checked-overflow and zero-division failures. Normally continuing paths carry earlier exception alternatives into later statements. Optional nonthrowing bool loops include the zero-iteration continuation, and mandatory loops do not imply later statement reachability. A handler participates only if at least one candidate exception can reach it after earlier typed handlers. Any unsupported operation/condition/control transfer resets the proof to unknown. A result with no arithmetic failures does not independently prove a try block exception-free. This is bounded analysis of existing VM semantics, not interprocedural nonthrowing inference.

2026-10-22 return refinement: bare return and normally completing constant-int arithmetic return operands terminate their path in the finite arithmetic analysis. Guaranteed return-operand zero division or checked overflow remains an exact exceptional outcome, with left-to-right evaluation and earlier exception alternatives retained. Unknown return operands, including calls, retain conservative catch reachability. This does not add interprocedural nonthrowing inference or alter runtime dispatch.

2026-10-22 loop-transfer refinement: finite arithmetic flow distinguishes break and continue from function return/nontermination. Each nearest while consumes its own transfers. Break allows continuation after that loop; continue revisits its nonthrowing condition. Optional-condition exits retain continuation, while a mandatory loop with only continuing/nonreturning paths does not expose later statements. Nested loop breaks do not escape their containing loop. Supported branches retain earlier and alternative arithmetic failures; unknown operations remain conservative.

2026-10-23 nested-handler refinement: finite arithmetic flow composes nested try/catch using existing ordered exact/base-type dispatch and shadowed-handler exclusion. Matching original failures are consumed; handler-raised failures escape the nested try rather than re-entering later sibling catches. Normal completion and supported return/break/continue flows are preserved. Unknown bodies and unknown handlers remain conservative. Empty arithmetic candidate sets do not independently prove a general nonthrowing contract; all source handlers still receive ordinary parsing/type checking.

A separate nonthrowing proof accepts typed int local let declarations whose constant arithmetic initializers are proven successful, and typed bool local let declarations whose initializer is independently proven nonthrowing by the supported boolean analysis. Unknown initializers, arithmetic faults, other declarations and assignments do not qualify for this separate proof. This lets ordinary catch-state merging agree with bounded nested-handler exception analysis without treating every empty arithmetic candidate set as a general nonthrowing proof.

2026-10-23 rethrow refinement: bare throw propagates the active caught arithmetic family through supported branches, loops and nested try bodies. Exact ZeroDivisionException/OverflowException catches constrain this family even after an unknown call. Base-type/catch-all handlers require finite candidates after excluding earlier matching handlers. Each nested catch replaces the context, including unknown contexts, and restores the enclosing context on exit. Unknown operations before rethrow remain conservative. This does not change runtime dispatch or introduce interprocedural nonthrowing inference.
