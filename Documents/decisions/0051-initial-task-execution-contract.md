# 0051: Initial Task execution contract

Status: Accepted by the user on 2026-11-13; initial declaration parser implemented, Task execution not implemented. Supplements accepted ADR0050.

## Initial language subset (TASK-01, TASK-04)
Use `task Name { construct(...) { ... } field name: Type; method name(...): void { ... } }` with one `method run(): void`. Ordinary methods are externally callable asynchronous notifications and self calls are synchronous. All Task methods initially return void, including self calls; synchronous free functions and Object queries retain their current return types. `start`, `stop` and `run` are reserved instance method names; start/stop are built-ins, and run cannot be called by source code. No inheritance, interfaces/traits, static members or properties in the initial Task subset.

Initial fields/constructor/notification parameters use the existing seven scalar types and statically named normal class/object references. Do not expand collection/generic/enum/struct signatures in this first subset. Task handles may be held and copied in local variables; prohibit them in any function/method/constructor parameters or returns, fields, collections, casts/boxing and captures. Resolve Task identity at runtime for self calls, including local aliases. `delete this;` is permitted only for a Task receiver; ordinary Object this-invalidation remains unchanged.

## Tick order and notifications (TASK-03, TASK-09)
At Tick entry capture run-eligible Task identities and a FIFO snapshot of pending notifications. Visit Task types in source declaration order and slots in ascending order. For each captured/live Task, process its captured notifications in FIFO order, then run it if its identity was run-eligible at Tick entry. Stopped Tasks still receive captured notifications. Notifications queued during Task processing wait for the next Tick; newly created Tasks/notifications after entry are excluded from this snapshot. After the Task phase, drain Object CallBuffers to quiescence and use the existing commit/reference-update phases. Task notifications to Objects may run in that same Tick. Nested Tick is forbidden throughout constructor/run/notification execution while a Tick is active.

Start/stop are idempotent requests affecting run eligibility from the following Tick. Last request wins. They do not override the entry snapshot for the current Tick. Delete immediately invalidates all aliases and skips later pending work for that identity, clears its queued notifications and supersedes start/stop. Start/stop/method calls through a deleted handle raise InvalidReferenceException. Repeated delete of an already invalid/deleted reference is a no-op, matching ordinary explicit reference clearing. Source state-inspection properties are deferred.

## Deletion and construction failure (TASK-02)
Deleting the currently executing Task unwinds its current Task entry and synchronous self-call frames, running finally blocks once and preventing remaining Task-body instructions. The Task is already Deleted while cleanup runs; accessing its fields or invoking its methods then raises InvalidReferenceException. Previously copied Object locals are ordinary references and remain usable. A finally exception follows existing synchronous finally precedence.

An active slot is withheld from reuse until those frames/finally blocks finish, then its fields/roots are cleared and its slot is pushed onto the LIFO stack. This is the necessary exception to immediate reuse on the next new: an executing slot cannot be overwritten while its frame still needs it. Inactive deleted slots are immediately reusable. Snapshot identities, not slot indexes, prevent replacement Tasks from running in the old Task's position during the same Tick.

If construction throws, no handle is returned; clear pooled fields and roots and return the slot after cleanup. Do not undo effects already performed on shared Objects or queued Object calls.

## Lifetime, storage and identity (TASK-05, TASK-06)
Each VM owns its Task pool. Both Running and Stopped Tasks remain alive until explicit delete or VM reset/disposal, even after source locals disappear; document this explicit lifetime to prevent accidental unbounded growth. Live Task fields and active Task frames retain strong references to ordinary Objects through the existing runtime root/graph mechanism; deletion releases only those edges, never destroys externally shared Objects.

Use a dedicated Task value kind with a monotonically increasing positive int64 identity, distinct from reusable pool indexes and normal Object handles. Never reset/reuse an identity during one VM instance; exhaustion throws before allocation. Reset removes all previous handles before any new execution. No per-slot generation number is added. Use configurable per-type chunks, default128 slots, with contiguous slot metadata and flattened field storage inside each chunk. Do not claim managed string/Object payloads become physically contiguous. Pool growth and constructor failure must leave other handles and pool/free-stack accounting unchanged. Final opcode/syscall IDs and bytecode compatibility checks are settled during implementation review; do not renumber existing IDs or promise old-VM support for new Task bytecode.

## Exceptions and invocation effects (TASK-07, TASK-08)
Existing synchronous catch/rethrow/finally behavior applies to Task entries and self calls. Initially use the existing Tick-fault policy for an unhandled Task exception: stop dispatching new work, discard remaining Task notifications and Object queues, skip commit and report the original failure at the Tick boundary. No exception is delivered back to the earlier external notification call site. Record TaskId, type/method, exception type and message in host-readable `LastTaskFailure`; no automatic logging, stack trace publication or observer callback is introduced. The VM remains faulted until reset, as with the current Object worker-failure policy. No automatic rollback is added.

For the initial Task try/catch/finally restriction, reject direct external asynchronous calls after target resolution, while permitting proven self calls and ordinary synchronous functions. This is an invocation-kind rule, not a transitive effect/atomicity guarantee: a synchronous helper can enqueue work outside that lexical block. Whole-call-graph effect checking remains explicitly deferred. Existing Object restrictions are unchanged.

## Validation (TASK-10)
Before product acceptance add every mandatory Task case from the user's instructions, plus snapshot notification boundaries, start/stop idempotence, stale alias rejection after LIFO reuse, self-delete/finally behavior, failed construction, faulted Tick/reset, root retention/release, unsupported syntax/types and bytecode rejection boundaries. Use deterministic barriers/outputs, not timing sleeps, for scheduling tests. Keep current Object/CallBuffer/Volatile/GC regression tests. Record throughput, allocated managed bytes and memory for repeated1k/10k/100k create/delete/Tick workloads, with warmup and multiple samples; report hardware/runtime and variability. Do not make a speedup claim before measurement. Object pooling and CallBuffer batching stay separate phases.

## Adoption boundary
The user adopted these initial semantic details under0050. It does not implement Tasks, expand the fixed150-item progress baseline, authorize an MSI rerun/release or modify unrelated WIP. TASK-01..09 are resolved for this initial subset; TASK-10 tracks the remaining test implementation and measurement. Broader language types, transitive effects, recovery after a faulted Tick and optimizations remain follow-ups.

## Current implementation stage
The declaration reader and reserved keyword are integrated. Header/type/name checks and body token ranges are available internally; bodies are not bound and no Task bytecode is emitted. Valid Task programs currently receive an explicit execution-lowering-not-implemented compile error in both VM and direct-WASM entry points. This does not satisfy Task execution/lifecycle/pool/scheduler acceptance or whole-program Task transfer/effect analysis. `Test_CompilerLib/TaskDeclarationTests.cs` covers60 cases; local full validation is recorded separately in `.local/task-declarations-20261113/acceptance.json`. Existing Object runtime behavior and syscall/opcode IDs are unchanged.
