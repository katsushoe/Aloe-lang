# AloeRepl.Core


Shared C# REPL engine used by both the native console host and the browser/WASM host.


Current REPL/compiler subset:


- user-defined functions with typed parameters and `int` / `string` / `bool` / `void` returns
- function calls, forward references, recursion, and nested early `return`
- `var`, `let`, assignment
- `if / else if / else`
- `while`, `break`, `continue`
- `print`
- int / string / bool expressions
- `+ - * / %`
- `== != < <= > >=`
- `not`, `and`, `or` with short-circuit evaluation


Function and class declarations entered in the REPL are persisted as module-level declarations. Ordinary statements are still persisted inside the synthesized `main`. Expressions entered without a trailing semicolon are printed automatically.

A submission containing `function main(...)` is treated as a complete Aloe program and is compiled without wrapping it in a synthesized `main`. Module-level class/function declarations already entered in the session are prepended, so the submitted `main` can use them. Standalone execution does not replace or mutate the existing interactive session history.

The current compiler supports a focused class/runtime subset: `field name: T;`, one synchronous `construct(...)` constructor, `this.field` reads/writes in instance code, `new Type(args)`, getter-only `public property`, synchronous private/protected instance methods callable from the same instance, `public async method ... : void` calls from a statically known class instance, and `public static async method ... : void` calls by class name. Basic single inheritance resolves inherited fields, getter properties, and instance methods; derived instances can be assigned to a base-typed local. `public virtual async method ... : void` and matching `public override async method ... : void` declarations support runtime dispatch for async calls, including calls through base-typed locals and inherited overrides in further-derived classes. The compiler includes all known concrete derived targets in async CallGraph cycle checks. Base classes must be declared first. Parameterless base constructors are called automatically. Parameterized base-constructor calls, property overrides, member hiding, synchronous virtual methods, field initializers, and direct external field access remain unsupported or unspecified. Tick dispatches instance calls through a bounded VMThread pool, serializing calls for each target Object; per-type Static CallBuffers are FIFO and serialize calls of the same type while different types may run in parallel. Calls enqueued during a Tick run before it returns. Worker stacks are isolated, Heap operations and Host syscall callbacks are synchronized, and blocking pipe operations from workers fail. If a worker throws, Tick joins active workers, discards queued calls, skips Volatile commit, and rethrows the first exception; completed Host side effects cannot be rolled back. Tick-time member writes use per-field Volatile State; self/internal reads observe the latest Volatile value, public property queries observe Committed State, and `tick()` commits dirty Volatile fields after both call buffer kinds drain. Reference-valued Volatile fields keep old Committed and new Volatile references alive until commit. Object field storage and class type metadata live with the Aloe heap Object table entry, and allocation reserves one 8-byte Aloe heap slot per field. Public instance property setters remain forbidden. The compiler rejects cycles in the statically resolved async CallGraph, including known virtual targets.

The compiler currently supports the `byte` type (0–255) for typed locals, fields, parameters, returns, and AloeBC constants. An integer literal in that range can initialize a byte or be passed to a byte parameter; out-of-range literals are rejected. Byte arithmetic and mixed byte/int arithmetic produce `int`. The `char` subset supports single UTF-16 code unit literals, typed locals/parameters/returns, char-to-char equality and ordering comparisons, and AloeBC constants; numeric conversion and arithmetic are rejected. Other conversions and broader value types remain unsupported.

The normal `enum` subset supports implicit and explicit int32 member values, `EnumType.Member` literals, typed assignments and function pass-through, and equality comparisons within the same enum type. For example, `enum Code { Zero, First = 10, Next, Alias = First, Negative = -(First - 8) }` assigns 0, 10, 11, 10 and -2. Explicit values accept compile-time integer expressions as described below. The first implicit value is 0 and each later implicit value is the preceding value plus one. An implicit value beyond int32 is a compile error; an explicit value can reset numbering after int32 maximum. Different member names may share a value and compare equal within the same enum. `with (EnumType) { ... }` adds short access through either `Member` or `.Member`; nested enum contexts resolve through the innermost type first. Mixing enum values with integers or another enum type in runtime expressions is rejected even when their numeric values match.

The basic `bitfield enum` subset uses signed int32 bit patterns and preserves enum type identity through locals, fields, function arguments/returns, async calls and type-based `with`. For example, `bitfield enum Flags { Zero = 0, Read, Write, Exec = 1 << 3, Next, Both = Read | Flags.Write }` assigns 0, 1, 2, 8, 16 and 3. An omitted first value is 1; later omitted values select the bit above the preceding value's highest set bit (zero resets to 1). Explicit values accept compile-time integer expressions, including bitwise operations and shifts. Masks and same-value aliases are allowed. `1 << 31` represents -2147483648; an implicit value after bit 31 is rejected. In runtime expressions, `|`, `&`, `^` and unary `~` operate only on values of the same bitfield enum, with 32-bit results. `&` binds before `^`, then `|`; comparisons bind more tightly, so write `(mask & Flags.Read) == Flags.Read`. Runtime arithmetic, ordering and cross-enum mixing are rejected; runtime shifts accept an int count as described below. Ordinary-int bitwise source expressions are also supported; int values cannot be mixed with bitfield enums. The prototype bytecode adds BitAnd/BitOr/BitXor/BitNot at 0x40 through 0x43 and BitShiftLeft/BitShiftRight at 0x44/0x45; AloeBC round-trip and VM execution support them, and the direct WASM backend now lowers all six opcodes for modules with Int/Bool function type metadata.

Runtime `<<` and `>>` require an int or bitfield enum left operand and an `int` count, preserving the left operand's type. For example, `let count: int = 1; let shifted: Flags = Flags.Read << count;` produces `Flags.Write`. Counts must be 0..31; negative or larger counts produce a VM error, including for literal counts. Left shifts discard bits beyond 32, and right shifts extend the sign bit (`Flags` value -2147483648 shifted right by 31 becomes -1). Shifts associate left to right; addition/multiplication bind more tightly, while comparison and `&`/`^`/`|` bind less tightly. Thus `Flags.Read << 1 + 2` shifts by 3, and `Flags.Read << 1 == Flags.Write` compares the shifted result. Calls, fields, async methods and `with` expressions retain the same shift rules.

Ordinary `int` expressions support `&`, `|`, `^`, unary `~`, `<<` and `>>`. Binary masks require two int operands and return int; complement requires int and returns int. Operands must fit signed int32 at execution. Shift counts must be int values in 0..31; left shifts discard higher bits and right shifts extend the sign bit. Invalid operands/counts raise VmException in the VM and trap in direct WASM. Byte, bool, char, float, decimal, normal enums and int/bitfield mixing are rejected during compilation; there is no implicit byte promotion for these operators. Precedence is unary, multiplication/division/modulo, addition/subtraction, shifts, comparisons, `&`, `^`, `|`, then logical operators. Write `(value & mask) == mask` for bit tests. All six operators use existing bytecode instructions and function metadata, including inferred locals, calls, loops and branches.

Enum initializers are evaluated during compilation. Both enum forms accept decimal/hexadecimal/binary signed int32 literals, parentheses, unary `+`/`-`, `+`, `-`, `*`, `/` and `%`. References must name an earlier member of the same enum, either `Member` or `EnumType.Member`; self references, forward references, other enum types and runtime values/calls are rejected. Initializer references are evaluated as int32 constants; runtime enum type restrictions still apply. Every arithmetic step must fit int32, division truncates toward zero, and zero divisors are compile errors. Bitfield initializers additionally accept `~`, `&`, `^`, `|`, `<<` and `>>`; shift counts must evaluate to 0..31, left shifts discard bits beyond 32 and right shifts extend the sign bit. Precedence from highest to lowest is unary, multiplication/division/modulo, addition/subtraction, shifts, `&`, `^`, `|`; binary operators associate left to right. Comparison, logical and assignment expressions are not initializer constants. Evaluated values are stored using existing AloeBC integer constants; no bytecode-format change is needed.

Type-based `with` also accepts a class name: `with (Logger) { .emit(1); }` calls an existing public static async method, with the same argument checks, CallGraph validation and deferred execution until `tick()` as `Logger.emit(1);`. Type targets are resolved at compile time. Dot-prefixed members are searched from the innermost context outward, so class and enum contexts may be nested together. Instance members cannot be accessed through a type context, and a local value with the same name as the target type makes the target ambiguous.

Instance `with (expression) { ... }` accepts a statically known class instance, including `new`, a function result, a local, or `this` in instance code. The target is evaluated once and retained in a local slot; reassigning the original variable does not change that target. `.Property` reads a public getter and `.Method(...)` queues an existing public async instance method with the same argument checks, virtual dispatch, CallGraph validation and Tick behavior as an explicit instance call. Private field reads/writes through `.field` are restricted to code in the field's declaring class; getter setters remain forbidden.

Multiple targets may be mixed in one block, for example `with (box, Logger, Color) { print(.Value); .emit(.Green); }`. Instance expressions are evaluated once from left to right before entering the block; type targets require no runtime evaluation. Lookup searches the innermost block first. Within a block, exactly one target must contain the requested member name; duplicate candidates are rejected as ambiguous, including identical targets and names shared across getters, methods or enum members. Method arguments do not disambiguate target names in this subset. Bare enum aliases also reject duplicate enum candidates, while ordinary local variables retain precedence. Explicit target member access can resolve a collision. Nested blocks restore their outer targets when they end. Struct and container targets remain unsupported, as do abbreviated synchronous private/protected method calls.

Structs now support synchronous `construct(...) { this.field = expression; ... }` and `new Type(arguments)`. Every field must be initialized before completion; initialized fields can be read and reassigned. Constructor bodies may declare locals and call synchronous functions. Parameters accept primitive values and structs; arguments evaluate once from left to right and preserve value copies. Duplicate constructors/parameter names, wrong argument counts/types, missing initialization and uninitialized reads are rejected. Constructors support `if/else`, `while` and `foreach` with definite-initialization checks. At a branch join, a field counts as initialized only when all continuing paths initialize it. Since `while` and `foreach` may execute zero times, assignments inside them do not initialize a field for code after the loop. Uninitialized field reads are rejected. Constructors allow early `return;` only after every field is initialized on that path. Nested assignments such as `this.field.path = expression` are supported after the containing field has a complete struct value; immutable values are rebuilt along the path. Uninitialized containing fields and return expressions are rejected. Empty structs without a constructor accept `new Empty()`; structs with fields need a constructor or a complete literal. Constructors return newly assembled immutable snapshots through existing VM calls and StructCreate instructions, with unchanged AloeBC encoding.

The basic `struct` subset supports `struct` and `sealed struct` declarations with `field` members of int, byte, char, float, decimal, bool or another struct type. Construct values with a literal such as `Point { x: 1, y: 2 }`; every field must be initialized exactly once. Initializers evaluate once in written order even when the declaration order differs. Empty structs and forward references between struct types are allowed; recursive value layouts are rejected. Locals support field reads and writes, including nested paths such as `pair.left.x = 3`. Fields retain nominal struct identity; assignments, function parameters/returns, class fields and queued async arguments preserve independent snapshots. Struct fields cannot contain references (including string/class/object/pipe), normal enums or uninitialized values. Byte literals use the existing checked context conversion, and struct int fields must fit int32.

Struct values use immutable field storage: replacing a field creates a new value and rebuilds the containing path, so the original and other copies remain unchanged. This applies even to nested structs without heap ObjectIds or reference graph edges. Methods and properties on structs, inheritance, layout annotations, struct/container `with`, equality and direct WASM lowering remain unsupported. The current prototype adds `EnumValueKind.Struct = 10` and `StructCreate/StructGet/StructSet = 0x50/0x51/0x52`. AloeBC preserves compiled struct literal/field instructions using existing primitive constants; runtime struct values are not codec constants. Older runtimes reject these new opcodes. The implementation scope and storage decision are documented in the [struct specification note](../Documents/en/Aloe-lang-spec.html#struct-subset).

The compiler still emits a complete `main`. For each interactive submission the REPL recompiles the successful source history, rebinds the verified module, and executes only the new instruction suffix. The same `AloeVm`, heap, successful entry locals and pending async CallBuffers remain across submissions, so earlier statements and Host API effects such as `readLine()` are not repeated. Expressions run at the current instruction boundary without becoming history. A complete program containing `main` runs in an isolated VM and leaves the interactive session unchanged.

A compile error leaves the active session unchanged. A runtime error faults the interactive session; use `:reset` to discard it. The REPL does not replay prior source to recover from a runtime error, because that could repeat input, sleep, or other host effects. Interactive resumption currently requires that no pipe execution context remains active. See the [persistent REPL decision](../Documents/decisions/0013-persistent-repl-vm.md).

The native REPL uses the VM settings loaded by `AloeVmSettings.Load()`. The browser REPL explicitly disables Host API capabilities because its synchronous execution loop has no browser input adapter and a blocking timer would freeze the UI. As a result, `readLine()` and `sleep(ms)` fail with a capability error in the browser REPL; the native host retains the configured capability behavior.

## Host memory diagnostics

When an executed program enables `GC.debug`, the REPL appends a `[REPL-PERF]` line after the VM's `[PERF] Program end` summary. It separates compile, VM construction, and VM execution timing/allocation (`compileAllocatedBytes`, `vmCreateAllocatedBytes`, `runAllocatedBytes`, and `totalAllocatedBytes`) and reports managed-memory start/end values. Normal submissions that do not request GC diagnostics keep their existing output.

`:hostgc` is a diagnostic-only REPL command. It explicitly runs the host .NET GC (`Collect` / pending-finalizer wait / `Collect`) and reports `beforeBytes`, `afterBytes`, `reclaimedBytes`, and Gen0/1/2 collection deltas. Normal Aloe execution never forces host GC through this command path.

Direct WASM bitfield lowering validates signed int32 operands before conversion, checks shift counts in 0..31 and traps on invalid values. Results return as sign-extended i64 values; left shifts discard bits beyond 32 and right shifts extend the sign. Runtime imports, objects and other value kinds remain unsupported. Encoding follows the [WebAssembly numeric instruction specification](https://webassembly.github.io/spec/core/binary/instructions.html).

The source frontend emits function type metadata for synchronous free functions whose parameters, local slots and return values use int, bool or int-backed enums (void returns are allowed). Short-circuit boolean expressions include their hidden Bool local slots. Unsupported functions retain legacy metadata for VM compilation. AloeBC preserves both forms, and normal VM compilation retains the required `main(args: string[]): int` signature.

`AloeCompiler.CompileForWasm(source)` compiles the supported subset directly for the WASM backend. The required `main(args: string[]): int` declaration retains the existing compiler behavior: `args` is syntax-only, creates no parameter/local slot and cannot be read or assigned. No local-slot remapping is needed. Calls to main, classes and unsupported parameter/local/return types are rejected. `aloe2wasm source.aloe -o output.wasm` uses this API; typed `.aloebc` input remains supported. Functions, recursion, structured loops/conditionals, short-circuit logic and int/bitfield bitwise operators are supported without manual metadata annotations. Integer arithmetic in the VM and direct WASM now checks both operands and results against signed int32 limits. Byte operands promote to int. Integer division truncates toward zero (`7 / 2 == 3`, `-7 / 2 == -3`), and remainder follows the dividend sign. `-2147483648 / -1` overflows; `-2147483648 % -1` is zero. VM range violations raise OverflowException and zero divisors raise ZeroDivisionException; WASM traps. This replaces the previous int64 subtraction/multiplication and floating result for nonintegral integer division. Mixed float/decimal arithmetic retains its existing rules. Integer constant storage and the WASM i64 ABI remain unchanged. Runtime imports/Syscall lowering and wider numeric support remain pending.

The CompilerLib WASM execution tests require Node.js on PATH, or an executable path in ALOE_TEST_NODE. They instantiate generated modules in the Node.js WebAssembly engine and compare results and invalid-input failures with the VM.
